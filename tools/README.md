# 控制链路 GUI 联试

运行 `python tools/control_link_gui.py`，仅依赖 Python 标准库的 Tkinter。

1. 工具固定监听 `127.0.0.1:2345` 的周期 `0x0001` 和 `127.0.0.1:1234` 的一次性 `0xFFFF`；两种报文无需修改设备台账目标。
2. 在窗口填写 DCMP 内部 UDP 入口，默认 `127.0.0.1:7788`；可编辑 1#～4# 各自的经纬高和航向/俯仰/横滚，并勾选在线位。点击“开始监听”后每秒发送 DP 152 字节、SP 132 字节心跳：DP 按[实时位姿合同](../doc/contracts/DP心跳实时位姿契约.md)填写 24 个逐面位姿字和 `POS2` 标记，SP 保持原布局。可取消勾选其中一路观察周期发送暂停。
3. 在 DCMP 激活新建或沿用的任务：双心跳在线后应连续收到 `0x0001`；开始采集后另收到一次 `0xFFFF 开始工作 workStandbyMode=1`，停止采集后另收到一次 `0xFFFF 待机 workStandbyMode=0`，而 `0x0001` 仍继续。完成任务后 `0x0001` 停止。
4. 在 DCMP **开始采集**后点击“发送 CSV 航迹”：读取脚本同目录 `target_data.csv`，按文件顺序向配置的 DCMP 入口发送 656 字节 `0x0100`，固定为 1# 阵面，目标 ID 来自 CSV。任务必须绑定 1# 阵面；未开始采集时 Core 按合同拒收。再次点击只停止航迹，不停止心跳；文件结束或手动停止时对仍活动的目标各提交一次消亡包。

窗口按字段页签显示 944 字节 `0x0001` 和 68 字节 `0xFFFF` 的最近有效报文；接收成功不代表设备执行成功。无效报文只在单行事件状态显示原因，不改变最近有效字段值。端口被占用时先关闭占用它的程序。

## CSV 映射与发送节奏

| CSV 列 | 0x0100 航迹区字段 / 相对偏移 | 约定 |
| --- | --- | --- |
| ID | targetId / 0 | 非负 int32；保留原目标号 |
| Range | range / 20 | 斜距 m |
| Azimuth | azimuth / 24 | 阵面局部方位，度；合法范围 -45～45 |
| Elevation | elevation / 28 | 局部俯仰，度；合法范围 0～45 |
| speed | radialSpeed / 32 | 径向速度 m/s，直接保留抵近正、远离负的原值 |
| RCS | amplitude / 36 | 仅用于构造未标定幅值原值，不声明两者物理标度一致，不做 dBsm 换算 |
| packFlag | packFlag / 116 | 1 存在，0 消亡；有最近有效包时消亡复用其坐标 |
| Time | 不映射 | 完全忽略，不校验、不排序、不参与发送调度，也不填写设备时间字 |

其余字段保持零；不把 CSV 的 X/Y/Z、Lon/Lat/Hgt、光学字段或分类字段擅自改成当前 Core 业务字段。
报文使用 44 字节公共头、384 字节状态前缀、224 字节航迹区和 4 字节包尾，计数由工具逐包分配。

发送完全忽略 Time，按文件顺序每 200 ms 处理最多 32 行，不逐行休眠、不按原时间回放、不自动循环；
界面显示 CSV 运行或停止状态和行号。只流式读取当前行，并为各活动目标保留最近有效包。
32 行包含被跳过的无效观测；因此有效包速率不固定为每秒 160 包。工具自身延迟后不追补历史批次。
2026-10-14 提交前的当前输入有 18,669 行、382 个目标，其中 5,390 行原始角度超接收范围；无效观测跳过并显示数量，不钳位、
不修改 Core 门禁。消亡复用有效坐标的记录不按原消亡坐标越界而跳过。界面只显示最近一条跳过原因。

## 心跳超时排查结论（2026-10-14）

- 原工具没有定时自动停止心跳的逻辑；停止模拟航迹与 DP/SP 勾选项独立。“停止”监听或关闭窗口才关闭全部套接字。
- 原 poll 先逐包刷新大字段表，再发心跳；DP 位姿解析失败会跳过同轮 SP 发送，UDP 异常会停掉整个工具，
  未处理的回调异常可能使下一次 after 没有安排。上述路径能造成中断，但仅凭昨天截图不能确认实际触发项。
- 现实现先尝试心跳，DP/SP 各自处理校验和发送错误；接收全部计数但每轮每种控制只刷新最后一包，
  发送 Socket 非阻塞，并在 finally 续接 after。CSV 读取或发送失败只停止 CSV，不关闭心跳。
- 工具仍使用单一 Tk 事件循环，没有新增线程。窗口模态操作、系统挂起或进程暂停仍可能延迟心跳；
  调度间隔达到 2 秒时显示诊断。Core 的 2 秒迟到、5 秒超时门槛保持原样。

本次只做 Python AST/中文注释检查、输入数据只读统计和静态差异检查；未启动 GUI、发送 UDP 或运行测试。

### 取消历史时间调度

用户截图中“航迹已发送 1313、CSV 跳过 503”对应前 1816 条数据已处理，即 CSV 第 1817 行。
第 1817 行 Time 为 15:08:02.105，第 1818 行为 15:09:17.802，原先按记录时间等待会空等 75.697 秒；
CSV 并非 EOF，也没有自动停止。用户随后明确只借用航迹数据，不使用 CSV 时间；现已删除历史时间调度，
统一采用工具自身每 200 ms 一批的发送节奏，并显示发送进度。
截图中的 DP/SP 超时不能由 CSV 到期等待解释，因为该分支不停止 poll；仍需单独确认 Tk 窗口阻塞或实际运行异常。
用户已反馈停止前拖动或缩放过工具窗口；这与单 Tk 事件循环暂停的风险吻合，但尚未做运行复现，不能标为已修复。

## 工具持续发送但 Core 心跳超时的定位

用户后续反馈 CSV/心跳发送计数持续增加而 Core 超时，不能继续只归因于窗口操作，也不能仅凭截图判定吞吐上限。
当前节奏最多处理 160 条 CSV 记录/s，656 字节航迹载荷最多约 105 KB/s；越界跳过时实际有效包更少。

- 工具新增独立一行“心跳最近本地提交”：分别显示 DP/SP 最近 sendto 成功时刻及固定目标地址。
  累计发送数只代表本地提交，不证明 Core 已收到。CSV 计数增长也不能单独证明心跳仍在发。
- 用户重新编译最新 Core 后，在启动 Core 的终端查看 `[UDP接收]`：实际来包触发每 5 秒至多一条汇总，
  包含 UTC 毫秒、来源、实际接收总数、通过协议校验的 DP/SP 数、航迹发布/入口拒绝数、协议拒绝数和最近拒绝码。
  `[UDP传输错误]` 保留原始 Socket 错误及端点状态，相同错误文字只报告一次，避免风暴。
- 端点状态包括端口、active、Socket 状态枚举、draining、continuation、pending 及读取失败次数。
  该汇总位于同步接收回调内，正常情况下 draining=1，不能把单条汇总的该值当成锁死证据。
  readyRead 为 Qt 通知累计数，emptyReads 为非阻塞读取暂时无包累计数，不等于丢包数。
  Core 已修正空唤醒不读取的边界：每轮首次至少尝试一次 readDatagram，以复位 Qt 5.14.2 通知状态；
  该候选修复仍待同一 CSV 负载复现验证，不能仅凭静态检查认定已解决此次中断。
- 工具 DP/SP 提交时间前进，但 Core 汇总停止而超时事件继续：缩小到报文抵达/Socket 接收通知路径，
  仍须结合原始错误或进一步抓包区分；汇总继续且协议拒绝增长：查看拒绝码及当前发送版本；
  总数及航迹增长而 DP/SP 数不增长：排查心跳是否真正发出、投递目标及门禁结果。

这些是可删除的低频终端诊断，不新增日志缓存、Topic、线程或第二条收包路径；没有提高队列容量、
放宽心跳阈值或声称已经解决停读。代理未编译或运行复现，需要用户提供超时前后终端输出和工具提交时刻。
