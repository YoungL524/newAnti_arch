# 业务线梳理方法

本文档用于约束后续业务线的描述方式，避免从 UI 控件、协议字段、测试程序等多个角度同时发散，导致设计复杂度失控。

## 一、核心原则

业务线应优先从系统内部的业务对象和状态变化出发，而不是从 UI 控件或外部协议字段出发。

推荐顺序：

```text
业务对象
  ↓
状态机 / 数据流
  ↓
输入输出契约
  ↓
单元测试
  ↓
集成测试 / 测试程序
  ↓
UI 展示
```

UI 是业务状态的可视化入口和操作入口，但不应该成为业务规则的承载者。

外部协议是设备通信契约，但不应该直接决定内部业务模型。

## 二、每条业务线的标准模板

每条业务线统一按以下模板描述：

```text
业务名称：
触发源：
输入数据：
内部状态：
处理规则：
输出事件：
是否需要落库：
是否影响 UI：
异常/超时规则：
```

### 字段说明

- **业务名称**：描述一个稳定的业务能力，例如“雷达工作状态控制”“航迹生命周期管理”。
- **触发源**：说明由谁触发，例如 UI、命令行、定时器、通信回包、自动任务。
- **输入数据**：说明该业务依赖哪些输入，可以是用户请求、总线数据包、配置项、定时事件。
- **内部状态**：说明该业务自己维护的状态，例如 Standby、Working、Lost、Selected。
- **处理规则**：说明状态如何变化、数据如何转换、哪些条件触发哪些动作。
- **输出事件**：说明该业务向外发布什么事件或数据包，例如状态变化、航迹快照、告警。
- **是否需要落库**：说明是否进入数据库，进入哪类表，保存原始数据还是业务结果。
- **是否影响 UI**：说明 UI 订阅哪些状态或快照，但不描述具体控件细节。
- **异常/超时规则**：说明发送失败、无回包、数据异常、航迹超时等情况如何处理。

## 三、业务线文档、单元测试和测试方案的对应关系

每条业务线建议至少形成三类材料：

```text
业务线文档
  ↓
单元测试文档
  ↓
测试方案 / 测试程序
```

### 1. 业务线文档

业务线文档回答：系统应该做什么。

它关注：

- 业务对象是什么；
- 输入是什么；
- 状态如何变化；
- 输出是什么；
- 异常如何处理；
- 是否影响 UI 或数据库。

### 2. 单元测试文档

单元测试文档回答：如何证明单个业务对象是对的。

它关注：

- 正常输入是否产生正确状态；
- 边界输入是否被正确处理；
- 错误输入是否被拒绝或降级；
- 超时逻辑是否符合预期；
- 输出事件是否正确。

### 3. 测试方案 / 测试程序

测试方案和测试程序回答：如何模拟真实数据流验证系统协作。

它关注：

- 是否需要模拟雷达数据；
- 是否需要模拟 UI 操作；
- 是否需要验证数据库写入；
- 是否需要验证网络发送；
- 是否需要长时间运行稳定性测试。

## 四、外部协议与内部业务的隔离原则

系统中已经存在通用数据包 `DataPacket`，用于在 `SystemBus` 上承载统一格式的数据。

正确理解是：

```text
外部设备协议
  ↓
core/protocol 中的协议结构体
  ↓
RadarDataProcessor / 适配器解析
  ↓
DataPacket / SystemBus
  ↓
内部业务对象
  ↓
UI / 数据库 / 反向控制
```

这样做的目标是：外部协议、设备厂家、端口、路由方式发生变化时，尽量只修改协议适配层和配置，不影响内部业务线。

## 五、哪些内容应该放在 core/protocol

`core/protocol` 应该保存外部协议的正式定义。

适合放在这里的内容：

- 设备发送给上位机的原始结构体；
- 上位机发送给设备的原始结构体；
- 协议包头；
- 协议字段枚举；
- 与协议二进制布局强相关的定义。

不适合放在这里的内容：

- 航迹生命周期规则；
- 威胁等级判断；
- UI 显示状态；
- 业务状态机；
- 数据库写入策略。

## 六、哪些内容应该放在 config

`config` 应该描述运行时装配关系，而不是业务规则本身。

适合放在这里的内容：

- 端点地址、端口和协议类型；
- endpointId 到 sourceType 的映射；
- payloadType 到发送目标的路由；
- DPH 周期发送配置；
- 默认设备选择。

不适合放在这里的内容：

- 航迹是否高亮；
- 工作状态如何切换；
- 威胁等级具体算法；
- UI 控件行为。

这些规则应该进入业务层代码，并由测试固定下来。

## 七、对 DataPacket 的定位

`DataPacket` 是系统内部总线的数据信封，不应该被理解为最终业务模型。

它负责描述：

- 数据来自哪里；
- 数据要发给谁；
- 数据类型是什么；
- 数据载荷是什么；
- 是否带有错误信息。

它不负责描述：

- 一条航迹当前是否丢失；
- 当前雷达是否处于启动中；
- 某个目标是否高威胁；
- UI 应该如何显示。

这些内容应该由业务对象进一步加工后产生新的业务事件或快照。

## 八、推荐的内部边界

推荐形成以下边界：

```text
外部协议层：StructureReceive / StructureSend
协议适配层：RadarDataProcessor / 后续可扩展 ProtocolAdapter
系统总线层：DataPacket / SystemBus
业务模型层：RadarStateController / RuntimeSettings / TrackManager
表现与操作层：UI / CLI / 测试程序
存储层：DataStore
```

核心目标是：

```text
换设备 → 尽量只改 protocol + config + adapter
改 UI → 不改协议层和业务规则
改业务规则 → 不改通信层和外部协议定义
```

## 九、建议优先固化的三条业务线

### 1. 雷达工作状态控制

目标：把“开始工作 / 待机”从简单字段写入升级为系统级状态机。

建议对象：`RadarStateController`

### 2. 运行时参数快照

目标：让 DPH 每 50ms 发送当前参数快照，而不是直接依赖 UI。

建议对象：`RuntimeSettings`

### 3. 航迹生命周期管理

目标：把外部协议中的单帧目标数据转成内部稳定航迹模型。

建议对象：`TrackManager`

## 十、后续文档建议

建议后续按业务线拆分：

```text
doc/business/雷达工作状态控制.md
doc/business/运行时参数快照.md
doc/business/航迹生命周期管理.md

doc/test/雷达工作状态控制-单元测试.md
doc/test/运行时参数快照-单元测试.md
doc/test/航迹生命周期管理-单元测试.md
```

初期不必一次性建全。先用本文档作为总方法论，再从“雷达工作状态控制”开始写第一条业务线即可。
