# NewAntiDrone 新架构设计 — 做减法版

## 1. 旧架构的问题

```
旧项目 NewAntiDrone/
├── NewAntiDrone/        ← 主程序 (exe)，包含核心层+UI+业务逻辑，全部混在一起
├── CommunicationMuilty/ ← 通信层 (static lib)
├── GraphicsMapView/     ← 地图组件 (static lib)
├── CustomizeTitleBar/   ← 标题栏 (static lib)
├── qt-material-widgets/ ← 第三方UI库 (static lib)
└── RSC/                 ← 资源 (static lib)
```

**问题清单**：

| 问题 | 原因 |
|------|------|
| 通信层编译成 lib，不能独立运行/测试 | 只有主程序是 exe |
| 添加新设备要改通信层源码 + 重编译 lib + 重编译主程序 | 设备配置硬编码在代码里 |
| 无法在 Lubuntu (headless) 上测试通信 | 主程序依赖 Qt Widgets |
| 核心逻辑、UI、业务全部耦合在主程序中 | 没有分层隔离 |
| WinSock 绑定 Windows | 已解决，迁移到 Qt Network |

## 2. 分类：什么该固定，什么该灵活

### 固定不动（编译一次，极少改动）→ 适合做 lib

| 模块 | 说明 |
|------|------|
| qt-material-widgets | 第三方 UI 组件库 |
| RSC | 资源文件 |
| CustomizeTitleBar | 标题栏样式 |
| GraphicsMapView | 地图渲染组件 |

### 需要灵活变化（跟业务走）→ 应在主程序中，配置驱动

| 模块 | 变化原因 |
|------|---------|
| 通信端点 | 每接一个新设备就要加 |
| 协议结构体 | 不同设备协议不同 |
| 数据处理 | 处理逻辑随需求变化 |
| UI 面板 | 随功能增减 |

## 3. 新架构：一个能跑的 exe

**核心思路**：把通信层放回主程序，通过 JSON 配置文件驱动。
添加设备 = 编辑 JSON 文件，不改代码。

### Phase 1：通信层可独立运行 ✅

NewAntiDrone-newArch/

### Phase 2：加入核心层（SystemBus + AppController）✅ 当前

```
NewAntiDrone-newArch/
├── core/
│   ├── main.cpp                  # 入口 → 创建 AppController
│   ├── AppController.h / .cpp    # 总控（从旧 NewAntiDrone 抽出业务逻辑，不依赖GUI）
│   │
│   ├── comm/                     # 通信层（Phase 1 已完成）
│   │   └── ...
│   │
│   ├── bus/                      # 系统总线（从旧项目直接复用）
│   │   ├── ISystemBus.h          # 总线接口（DDS 发布订阅模式）
│   │   ├── SystemBus.h / .cpp    # 总线实现（单例，State 状态机，工作线程分发）
│   │   ├── ThreadSafeQueue.h     # 线程安全队列
│   │   └── GenericPackets.h      # 通用数据包定义（DataPacket + 打包/解包模板）
│   │
│   ├── processor/                # 数据处理
│   │   ├── RadarDataProcessor.h / .cpp  # 正向流：收包解析 / 发布总线 / 写库
│   │   ├── BusToCommRouter.h / .cpp     # 反向流：总线订阅 / 路由发包
│   │   └── DphPublisher.h / .cpp        # DPH 定时发布
│   │
│   ├── data/                     # 数据访问与配置
│   │   ├── DataStore.h / .cpp    # 数据库存取层（SQLite / 网络数据库）
│   │   └── ConfigManager.h / .cpp# 配置文件管理（JSON 加载与缓存）
│   │
│   └── protocol/                 # 协议结构体
│       ├── StructureSend_C.h
│       └── StructureReceive_C.h
```

**关键特征**：
- `core` 是一个 **可执行程序**，不是 lib
- 可在 Windows (MinGW) 和 Lubuntu (GCC) 上直接运行
- 不依赖 Qt Widgets，纯 Console
- 通信端点完全由 `endpoints.json` 驱动
- **AppController** 是总控入口，管理通信层 + SystemBus 生命周期
- **SystemBus** 是数据高速公路，具备显式状态机（Running → ShutDown 不可逆），所有模块通过发布/订阅通信
- 业务装配由 `processor.json` 驱动（端点源映射 / 路由规则 / DPH 配置），缺失时自动回退到内置默认值

## 4. endpoints.json 配置格式

```json
{
  "endpoints": [
    {
      "id": "radar_cpu",
      "protocol": "udp",
      "localAddress": "127.0.0.1",
      "localPort": 7788,
      "targets": {
        "dph": { "address": "127.0.0.1", "port": 3456 },
        "workmode": { "address": "127.0.0.1", "port": 1234 }
      },
      "description": "雷达CPU通信"
    },
    {
      "id": "dome",
      "protocol": "udp",
      "localAddress": "0.0.0.0",
      "localPort": 8899,
      "targets": {
        "control": { "address": "192.168.1.100", "port": 5000 }
      },
      "description": "转台控制"
    }
  ]
}
```

**添加新设备**：在 `endpoints` 数组中追加一项即可，零代码改动。

## 5. 与旧架构的对照

| 旧架构 | 新架构 | 变化 |
|--------|--------|------|
| 通信层是 static lib | 通信层源码编译进 core exe | 可独立运行/测试 |
| 设备配置硬编码 | JSON 配置文件驱动 | 添加设备不改代码 |
| 主程序依赖 Qt Widgets | core 是 Console App | Lubuntu 可运行 |
| 所有逻辑在一个 exe | Phase 分步实现 | 渐进式开发 |
| 6 个全局变量 | EndpointConfig 结构体 | 已在 V2 解决 |
