# 07 - 核心实时链路加固（数据视角）

> 状态：目标架构与实施验收基线，尚未全部实现。消息入口已由 `08-现有航迹链路审计与统一入口.md` 修订为唯一 `DataPacket/SystemBus`；独立 `TrackPacketChannel` 已删除。  
> 适用范围：创建任务、开始/停止接收、50 ms 大包接入、航迹标准化、识别、实时显示、历史存储与回放。  
> WebSocket 周期性全量协议已于 2026-08-14 删除；当前实现为连接级 snapshot + 稳态 delta + revision。

## 1. 目标与底线

系统核心不是某个页面或算法插件，而是一条可长期稳定运行的数据主干：

```text
设备数据
  -> 接收/校验
  -> 厂家协议适配
  -> 标准权威航迹
  -> 类型安全发布
       |-> 实时显示投影 -> Web 增量传输 -> 页面渲染
       |-> 异步持久化 -> 历史查询/回放
       |-> 对外转发插件
       `-> 算法与业务插件
```

核心链路必须满足：

1. 连续运行时间增加时，内存、队列长度、单帧大小和处理时延不能线性增长；
2. 显示和存储互相隔离，数据库或磁盘变慢不能阻塞接收与实时显示；
3. 每一个队列、缓存、批次和消息都有明确上限及过载策略；
4. 插件只能消费稳定的只读数据契约，不能反向侵入或阻塞主干；
5. 创建任务、启停接收、接收并显示航迹、50 ms 大包数据流是永久回归基线；
6. 所有丢弃、合并、积压、断连和重同步均可观测，禁止静默失败。

“支持 7×24 小时”不是简单地运行 168 小时不崩溃，而是系统资源进入稳定平台，并且在规定输入压力下持续满足时延、完整性和可恢复性指标。

## 2. 从数据用途进行分层

同一份设备输入在不同场景中有不同的完整性、时效性和保留期限要求。不能用一个不断增长的数组或一种 Web DTO 同时承担所有职责。

| 层级  | 数据                                 | 主要用途               | 完整性             | 生命周期         | 数据所有者    |
| --- | ---------------------------------- | ------------------ | --------------- | ------------ | -------- |
| D0  | 原始线缆帧 `RawFrame`                   | 协议取证、问题复现、厂家兼容验证   | 按采集策略决定，启用时尽量完整 | 短期文件/归档策略    | 原始数据记录器  |
| D1  | 厂家解码对象 `GeneralPackage`            | 将厂家字段转换为内部标准字段     | 单次处理完整          | 函数/适配器内部临时对象 | 输入协议适配器  |
| D2  | 权威航迹 `TrackPacket`                 | 识别、存储、转发和插件消费的唯一事实 | 必须保持字段语义和顺序     | 只读事件；可持久化    | 核心航迹域    |
| D3  | 实时显示事件 `TrackDisplayDelta`         | 低延时地通知新增、更新和移除     | 允许显示层合并中间点      | 毫秒至秒         | 显示管理器    |
| D4  | 显示状态 `TrackDisplayState`           | 当前航迹、有限尾迹和交互状态     | 有界、可重建          | 内存常驻但严格有界    | 显示管理器/前端 |
| D5  | 历史查询模型 `TrackHistoryPage`          | 任务复盘、分页查询和回放       | 来自持久化权威数据       | 按任务与保留策略     | 历史数据服务   |
| D6  | 指标与事件 `PipelineMetric/SystemEvent` | 运维、告警、容量和故障定位      | 聚合后完整           | 滚动窗口/持久化     | 监控与事件服务  |

### 2.1 D0：原始数据不是实时显示数据

原始数据是设备送达的字节和必要元数据：

```text
endpointId, receiveWallTime, ingressSteadyTime,
protocol/version, byteLength, bytes, checksum/status
```

它适合协议复现和取证，但不能穿透协议边界进入显示、识别或普通插件。原始记录应采用独立的有界队列和顺序文件/分段文件写入，不能在 UDP 接收线程同步落盘。

是否保存 D0 必须是显式策略：关闭、抽样、故障窗口、完整记录。完整记录模式仍受磁盘吞吐量和容量约束；空间不足时必须告警并执行已配置的停止记录或循环覆盖策略，不能拖死主链路。

### 2.2 D1：厂家对象只存在于适配层

`GeneralPackage` 是解码过程的临时结果。它不能发布到全局总线，不能作为数据库长期模型，也不能被 Web 或插件直接依赖。厂家协议变化只能影响通信与输入适配模块。

### 2.3 D2：TrackPacket 是唯一权威航迹

`TrackPacket` 完成端点到设备/任务映射、单位统一和识别后，以 `shared_ptr<const TrackPacket>` 发布一次。它具有稳定 schema、`traceId` 和各阶段单调时钟时间戳。

约束：

- 发布后不可修改；
- 显示、存储和插件共享同一只读对象，不为每个消费者深拷贝；
- 消费者不得重新解析厂家协议；
- 消费者的失败不得改变权威航迹或阻塞其他消费者；
- 同一来源内保序，跨设备不强求全局物理时间一致；
- 墙上时间用于展示和历史查询，单调时间用于链路时延。

### 2.4 D3/D4：显示数据是可重建的实时投影

显示数据追求“最新、低延迟、连续观感”，不承担原始数据归档。中间点在页面来不及消费时可以合并，但必须保留每条航迹的最新状态，并记录合并计数。

每条活动航迹只保留固定长度或固定时间窗口的尾迹；总航迹数、总点数和交互状态数都必须有上限。航迹停止更新后的清理仅表示释放 UI 资源，不代表核心系统判定目标物理消失。

### 2.5 D5：历史数据不通过实时 WebSocket 补齐

历史查询和回放从持久化的 D2 数据构建，使用分页、时间范围和任务范围读取。实时 WebSocket 不承担无限历史，不允许因为页面打开时间变长而持续增大消息。

## 3. 核心主干与分支边界

### 3.1 不可破坏的同步主干

同步主干只执行有确定上界的工作：

```text
接收完整帧
  -> 基础校验
  -> 解码与标准字段映射
  -> 最小同步识别
  -> 发布只读 TrackPacket
```

同步路径禁止数据库写入、文件写入、Web JSON 序列化、网络转发、复杂插件算法以及无界等待。

### 3.2 核心异步消费者

以下能力属于基座，但通过彼此独立的有界通道消费 D2：

- 实时显示投影；
- 权威航迹持久化；
- 系统指标与事件记录。

它们是“核心分支”，不是可以任意删除的插件。每个分支拥有自己的 worker、队列、容量指标和故障策略。

### 3.3 可插拔消费者

识别算法扩展、第三方协议输出、告警分析、统计报表等属于插件/业务分支。插件只能通过版本化接口订阅 `TrackPacket` 或查询历史数据。

插件必须满足：

- 回调只做校验和有界投递；
- 不得占用 SystemBus worker 执行耗时任务；
- 自有队列满时只影响该插件，并产生明确指标；
- 插件加载、卸载和故障不改变基础显示及存储链路；
- 不允许把插件字段直接塞入核心协议，扩展信息使用版本化扩展或插件私有存储。

## 4. 实时显示协议 V2

### 4.1 废止周期性全量重发

旧实现每 1 秒扫描显示缓存并重复发送最多 600 个点。该周期性全量发送已经删除；当前仍对有界 600 点窗口做 diff，但只传输变化。

V2 改为：

1. 客户端连接、任务切换或重同步时发送一次**有界快照**；
2. 稳态只发送快照之后的**增量**；
3. 客户端按序列号应用增量；
4. 检测到序列缺口时停止猜测，主动请求新快照；
5. 慢客户端只丢弃过期显示增量并重同步，不能积压无限消息。

已落地契约：

```typescript
interface TrackDisplaySnapshot {
  type: 'tracks'
  mode: 'snapshot'
  revision: number
  timestamp: number
  tracks: TrackDisplayPoint[]
}

interface TrackDisplayDelta {
  type: 'tracks'
  mode: 'delta'
  revision: number
  timestamp: number
  upserts: TrackDisplayPoint[]
  removals: TrackDisplayPointKey[]
}
```

公共的 `taskId/deviceId/trackId` 放在航迹层，点数组只携带变化字段。颜色、大小等可由稳定规则在前端推导的样式不应逐点重复传输；交互状态只在变化时下发。

### 4.2 有界状态

具体容量必须配置并通过压测确定，不在代码中散落魔法数字。至少包括：

```text
maxActiveTracks
maxTrailPointsPerTrack 或 trailWindowMs
maxDisplayPointsTotal
maxDeltaPointsPerFlush
maxWebSocketFrameBytes
maxPendingBytesPerClient
trackStaleMs
displayFlushIntervalMs
```

容量达到上限时，优先级从高到低为：

1. 保留每条航迹的最新点；
2. 保留被选中/跟踪航迹的必要尾迹；
3. 合并普通航迹的中间显示点；
4. 删除最旧显示尾迹；
5. 无法连续应用增量的客户端转入重同步。

不得用“提高 WebSocket 警告阈值”替代容量治理。

### 4.3 前端渲染约束

- WebSocket 回调只负责解码、顺序校验和更新内存态；
- 同一浏览器帧内的多个更新可合并，只渲染最新状态；
- 地图绘制不遍历无限历史；
- 航迹表格按 `TrackKey(deviceId, trackId)` 聚合，不把每个尾迹点当成独立航迹；
- 页面隐藏或渲染变慢时，不允许 WebSocket 消息无限排队；
- 重连必须先清理旧 `streamId` 状态，再应用新快照。

## 5. 持久化链路

### 5.1 数据保存策略

建议把保存策略分开配置：

| 数据                | 默认建议      | 说明                 |
| ----------------- | --------- | ------------------ |
| 权威 `TrackPacket`  | 按任务完整保存   | 支持历史、回放和业务审计       |
| 原始 `RawFrame`     | 按部署策略     | 高容量，可关闭、抽样或按故障窗口记录 |
| 显示 Delta/Snapshot | 不作为权威历史保存 | 可由权威航迹重建           |
| 指标与系统事件           | 聚合/滚动保存   | 用于 7×24 运维与容量分析    |

### 5.2 异步写入

```text
SystemBus / DataPacket(Command::Track)
  -> StorageIngress（快速投递）
  -> 有界批量队列
  -> StorageWorker
  -> 批量事务/分区文件
  -> DataStore
```

存储队列应按条数和字节数双重设限，并暴露当前深度、高水位、批次耗时、写入速率、失败数和最老待写数据年龄。数据库短时不可用时允许在有界内存或本地日志中缓冲；超过设计恢复窗口后按明确的数据保障等级处理并告警。

不能同时宣称“任何磁盘故障下绝不丢数据”和“绝不反压接收”。部署必须选择并记录保障等级：

- **实时优先**：存储过载时停止/降级记录，接收与显示继续；
- **完整性优先**：使用预分配持久日志吸收峰值，日志也耗尽时主动停止采集并明确告警；
- 禁止默认采用无界内存排队。

## 6. 背压、过载与故障隔离

| 位置             | 正常策略         | 达到上限时               | 不允许的行为       |
| -------------- | ------------ | ------------------- | ------------ |
| 通信接收           | 快速收包并解码      | 计数、告警，按协议能力处理       | 阻塞等待数据库或浏览器  |
| TrackPacket 发布 | 类型安全有界队列     | 返回失败并记录来源/数量        | 无限扩容、静默丢弃    |
| 显示投影           | 合并并保留最新状态    | 丢弃过期中间显示点           | 丢掉最新点后继续伪装正常 |
| 单个 WS 客户端      | 增量发送         | 清除过期增量并要求重同步/断开慢客户端 | 拖慢其他客户端或核心总线 |
| 航迹存储           | 批量异步写        | 按保障等级降级或停采          | 在总线回调同步写库    |
| 插件             | 独立 worker/队列 | 隔离、熔断该插件            | 传播阻塞到核心链路    |

所有过载事件至少包含 `taskId/deviceId/endpointId`（适用时）、发生位置、容量、丢弃/合并数量和持续时间。

## 7. 可观测性

每个阶段使用同一 `traceId` 关联，并至少采集：

- 输入包/秒、字节/秒、校验失败数；
- `TrackPacket` 发布成功/失败数和通道高水位；
- 接收→标准化→识别→显示管理→Web 排队的 P50/P95/P99；
- 活动航迹数、显示总点数、每航迹尾迹点数；
- snapshot/delta 的点数、字节数、构建耗时和发送耗时；
- 每个 WebSocket 客户端的待发送字节、重同步和断开次数；
- 存储队列深度/字节、高水位、最老数据年龄、批量写入耗时和失败数；
- 进程工作集、堆使用量、线程数、CPU、磁盘吞吐和剩余空间；
- 插件各自的积压、丢弃、熔断与恢复。

周期日志只输出聚合值，避免高频逐点日志反过来成为性能瓶颈。

## 8. 容量模型

测试负载不能只写“4 台设备”，必须完整描述：

```text
设备数 N = 4
每设备输入周期 = 50 ms（20 包/秒）
总包速率 = 80 包/秒
每包最大字节数 = B_max（从真实大包或协议上限确定）
每包最大航迹点数 = P_max（从真实大包或协议上限确定）
活动航迹数 = T_max
Web 客户端数 = C
是否同时保存 D0 / D2
```

压测输入速率为 `N × 20 × P_max` 点/秒。`B_max`、`P_max` 和 `T_max` 必须在第一阶段通过协议与真实样本固化，不能用当前偶然的小数据量代替设计上限。

资源应近似满足：

```text
显示内存 = O(T_max × 每航迹尾迹上限)，与运行时长无关
稳态 Web 带宽 = O(新增/变化点速率)，与已运行时长无关
历史存储 = O(运行时长)，但通过磁盘保留与归档策略管理
```

## 9. 7×24 验收标准

### 9.1 功能门禁

每次核心或插件变更都必须自动验证：

1. 创建并激活任务；
2. 选择设备并开始接收；
3. 4 设备 50 ms 大包连续输入；
4. 实时航迹出现且设备、任务、位置和姿态映射正确；
5. 停止接收后状态正确，缓存按策略回收；
6. 再次开始无需重启程序；
7. 开启存储后可按任务分页查询并回放；
8. 浏览器断开重连后通过 snapshot 恢复，随后继续接收 delta；
9. 存储故障和慢客户端不影响其他客户端的实时显示；
10. 基础链路测试失败时，插件/分支禁止合入。

### 9.2 性能与稳定性门禁

在第 8 节的设计负载下：

- 连续 168 小时无崩溃、死锁、线程失控和无界队列；
- 预热后内存进入平台区，不允许与运行时间呈持续线性增长；
- 接收至后端显示投影 P95 ≤ 50 ms，P99 ≤ 100 ms；
- 接收至浏览器状态可用 P95 ≤ 100 ms，P99 ≤ 200 ms；
- 页面航迹扫描、缩放和平移无持续堆积，渲染使用最新数据；
- 稳态 delta 大小由该周期变化量决定，不随历史点数增长；
- 快照、单帧、单客户端待发送字节和全部内存缓存均不超过配置上限；
- 开启 D2 存储后不突破上述显示时延；
- 慢客户端、数据库暂停和磁盘短时抖动注入时，故障被隔离并可恢复；
- 所有合并、丢弃和重同步数量与压测端统计能够核对。

测试分四级执行：30 分钟功能/性能冒烟、8 小时内存趋势、24 小时故障注入、168 小时正式耐久。168 小时测试不是每次提交都运行，但发布候选版本必须通过。

## 10. 实施顺序

### 阶段 A：测量并锁定基线

- 固化 `B_max/P_max/T_max` 和测试数据集；
- 记录当前 4 设备模式下 CPU、内存、端到端时延、WS 字节和存储吞吐；
- 将基础任务/启停/显示流程加入自动回归脚本。

### 阶段 B：显示状态有界化

- 用每航迹有界尾迹替换持续追加；
- 增加总航迹、总点数和交互状态上限；
- 增加公平淘汰和容量指标；
- 测试单条高频航迹不能挤掉其他设备的最新状态。

### 阶段 C：WebSocket V2 增量协议

- [完成] 实现 snapshot + delta + revision；
- [完成] 前端实现顺序校验、合并渲染和断线重同步；
- [完成] 删除周期性全量协议及 V1 兼容分支。

### 阶段 D：持久化隔离

- [完成] 将 D2 存储迁到独立有界队列和 worker；
- 批量写入并提供积压、失败和数据年龄指标；
- 根据部署选择原始 D0 记录模式和存储保障等级。

### 阶段 E：耐久与故障测试门禁

- 建立 4 设备 50 ms 大包发生器；
- 自动采集资源曲线和延迟分位数；
- 注入慢客户端、断网、数据库暂停、磁盘变慢及插件阻塞；
- 依次通过 30 分钟、8 小时、24 小时和 168 小时测试。

## 11. 与当前代码的主要差距

当前已经具备：

- `TrackPacket`、最小同步识别和类型安全 `DataPacket` 载荷；独立 `TrackPacketChannel` 已删除；
- `TrackDisplayManager`、WebSocket Bridge 和前端航迹图层；
- SQLite 航迹历史、任务查询和部分链路时延指标；
- 全局缓存点数、snapshot 点数和慢客户端待发送字节的初步上限。

仍需加固：

- 当前活动航迹会持续积累显示点，直到全局 50000 点预算；
- snapshot 构建会扫描大量缓存，并每秒重复发送最多 600 个旧点；
- 单点 JSON 含重复字段，实测约 335 byte/点；
- 48 KiB 仅是帧大小警告，256 KiB 仅是慢客户端积压阈值，不构成容量方案；
- 需要实现每航迹有界尾迹、公平总预算和 V2 增量协议；
- 需要确认当前存储是否完全脱离主干回调，并补齐故障注入测试；
- 需要把资源、队列、Web 和存储指标纳入统一压测报告。

## 12. 架构决策记录

以下结论作为后续开发评审规则：

1. 核心权威数据只有 `TrackPacket`，显示 DTO 和厂家包都不是第二份事实；
2. 实时显示与完整历史是两个用途，必须使用不同的数据保留和传输策略；
3. 显示允许有控制、可统计的合并，权威存储是否允许丢失由保障等级决定；
4. 运行时长只能增长历史存储，不得增长实时内存状态和 Web 单帧；
5. 插件故障不能越过有界队列影响核心接收、显示和存储；
6. 所有容量参数必须集中配置、可观测并由真实上限压测验证；
7. 不通过核心链路回归与性能门禁的功能不得合入主线。
