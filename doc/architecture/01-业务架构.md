# 01 - 业务架构

> 业务架构只描述系统做什么、管理什么、哪些业务能力彼此协作。  
> 本文不描述 `SystemBus`、`WebService`、数据库表、端口和类名。

## 1. 系统定位

本系统是反无人机雷达上位机 / 管理系统。

核心职责不是替代雷达或数据处理系统做航迹起批、融合、消失判断，而是：

- 管理设备；
- 组织任务；
- 下发控制与运行参数；
- 接收并展示航迹；
- 固化日志、告警和历史数据；
- 为 Web UI 和后续第三方提供稳定数据协议。

## 3. 核心业务对象

### Device

业务设备，不等同于通信端点。

负责描述：

- 设备 id、名称、类型；
- 厂家 / 型号；
- 经纬度、高度；
- 雷达阵面参数；
- 与通信端点的绑定关系；
- 当前运行状态。

### Task

任务是管理系统的业务上下文。

负责组织：

- 本任务关联哪些设备；
- 本任务使用哪些运行时参数；
- 本任务期间产生哪些航迹、日志、告警和操作记录；
- 当前任务状态。

任务状态建议：

```mermaid
stateDiagram-v2
    [*] --> Draft
    Draft --> Active: activate
    Active --> Completed: complete
    Active --> Archived: archive
    Completed --> Archived: archive
    Archived --> [*]
```

### Runtime Settings

当前有效运行参数快照。

注意：快照不是为了做网络 diff 优化，而是后端持有的一份“当前有效参数”。

业务规则：

- UI 只在用户调参时提交变化；
- 后端合成完整有效参数；
- 后端按最新参数持续驱动 DPH 发送；
- 没有新参数时继续使用旧参数。

### Track Display

上位机侧不负责航迹起批、消失、融合等数据处理算法。

上位机负责的是航迹显示数据管理：

- 接收标准航迹点；
- 根据点序号和交互状态决定显示样式；
- 维护选中、高亮、追踪使能等显示状态；
- 必要时把被追踪航迹转发给其他模块；
- 给 Web 输出固定显示协议。

## 4. 业务边界

### 上位机负责

- 设备台账；
- 任务上下文；
- 参数快照；
- 工作/待机控制；
- 航迹显示状态；
- 日志、告警、历史记录；
- 固定 core-web 协议。

### 上位机不负责

- 雷达内部航迹起批；
- 航迹融合算法；
- 目标消失判定算法；
- 厂家私有协议向 Web 透传；
- UI 直接操作外部协议结构体。

## 5. 稳定业务结论

后续实现必须遵守：

```text
设备信息由后端管理
任务是业务上下文
运行时参数由后端合成完整快照
DPH 按最近快照持续发送
航迹对 Web 输出固定显示协议
厂家协议差异只存在于 core 内部
```
