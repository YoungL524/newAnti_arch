# 05 - 核心流程

> 核心流程描述系统最重要的数据和控制路径。  
> 这些流程应长期稳定，局部模块可以替换，但主路径不应随意改变。

## 1. 上行航迹显示流程

```mermaid
sequenceDiagram
    participant Radar as 雷达 / test_comm
    participant Comm as 通信接入
    participant Adapter as 协议适配
    participant Bus as SystemBus
    participant Recognition as RecognitionModule
    participant Track as TrackDisplayManager
    participant WebBridge as TrackDisplayWebBridge
    participant UI as React Web

    Radar->>Comm: UDP 厂家协议数据
    Comm->>Adapter: raw bytes
    Adapter->>Adapter: 厂家协议解析与标准化
    Adapter->>Bus: publish NormalizedTrackBatch
    Bus->>Recognition: dispatch normalized tracks
    Recognition->>Recognition: identify or mark Unknown
    Recognition->>Bus: publish IdentifiedTrackBatch
    Bus->>Track: dispatch identified tracks
    Track->>Track: apply display rules
    Track->>Bus: publish DataPacket<TrackDisplaySnapshot>
    Bus->>WebBridge: dispatch TrackDisplaySnapshot
    WebBridge->>UI: WebSocket tracks fixed DTO
```

关键原则：

- Web 不接收厂家协议；
- 上位机不做航迹起批、消失和融合算法；
- 识别是标准航迹进入显示和对外转发前的唯一必经处理；
- 没有真实识别算法时由透传识别器输出 `Unknown`；
- 标准航迹和识别结果必须经过 `SystemBus`，不得使用 Processor 到 Manager 的业务旁路；
- 总线订阅回调不能同步执行长耗时算法或数据库写入；
- UI 接收的是显示快照（固定 DTO）；
- `TrackDisplayManager -> Web/UI` 必须经过 `SystemBus + TrackDisplayWebBridge`，不直接打 `WebApiController`。

## 2. 对外航迹转发流程

```mermaid
sequenceDiagram
    participant Bus as SystemBus
    participant Forward as ForwardingModule
    participant Adapter as OutputProtocolAdapter
    participant Comm as CommunicationManager
    participant External as 第三方软件 / 外部设备

    Bus->>Forward: IdentifiedTrackBatch
    Forward->>Forward: apply configured output policy
    Forward->>Adapter: standard identified tracks
    Adapter->>Adapter: encode vendor protocol
    Adapter->>Comm: EncodedFrame(endpointId, targetName, bytes)
    Comm->>External: UDP/TCP/vendor protocol
```

关键原则：

- 转发只消费识别后的标准航迹；
- 第三方协议差异只存在于 `OutputProtocolAdapter`；
- 显示、存储和日志不能成为转发前置条件；
- 引导属于可选的输出模块，可结合已识别航迹和交互命令生成引导协议；
- 当前代码尚未实现此航迹转发链路，`BusToCommRouter` 主要承担设备控制命令下行。

## 3. 航迹交互命令流程

```mermaid
sequenceDiagram
    participant UI as React Web
    participant API as WebApiController
    participant Bus as SystemBus
    participant Track as TrackDisplayManager
    participant WebBridge as TrackDisplayWebBridge

    UI->>API: PUT /api/devices/{id}/tracks/{trackId}/interaction
    API->>API: validate DTO + active task + device binding
    API->>Bus: publish command(taskId, deviceId, trackId)
    Bus->>Track: dispatch TrackInteractionCommand envelope
    Track->>Track: verify active task and cached track
    Track->>Track: update interaction state
    Track->>Bus: publish DataPacket<TrackDisplaySnapshot>
    Bus->>WebBridge: dispatch TrackDisplaySnapshot
    WebBridge->>UI: WebSocket tracks fixed DTO
```

关键原则：

- `WebApiController` 只校验请求并发布命令，不直接调用 `TrackDisplayManager`；
- 命令必须携带发布时的活动 `taskId`；Manager 仅接受与当前任务一致且仍在缓存中的航迹，防止延迟命令串入下一次任务；
- 航迹交互状态由 `TrackDisplayManager` 持有，经 snapshot 回推给 UI；
- UI 读显示数据与写交互命令均经 `SystemBus` 治理；
- REST 返回 `ok/accepted` 表示命令已成功发布到总线（`mode: queued`），不代表 interaction 已应用；最终显示状态以 WebSocket snapshot 为准。

## 4. 下行工作状态控制流程

```mermaid
sequenceDiagram
    participant UI as React Web
    participant API as WebApiController
    participant Work as RadarWorkModeController
    participant Bus as SystemBus
    participant Router as BusToCommRouter
    participant Comm as 通信接入
    participant Radar as 雷达 / test_comm

    UI->>API: POST /api/start or /api/stop
    API->>Work: requestWork/requestStandby
    Work->>Bus: publish workStandby command
    Bus->>Router: dispatch command
    Router->>Comm: sendTo(endpoint, target)
    Comm->>Radar: UDP workStandby
    Radar-->>Comm: workStandby echo
    Comm-->>Work: state echo through processor/bus
```

关键原则：

- 工作状态由后端状态机管理；
- UI 不直接拼 workStandby 协议包；
- 状态反馈最终同步给 Web。

## 5. DPH 参数更新与周期发送流程

```mermaid
sequenceDiagram
    participant UI as React Web
    participant API as WebApiController
    participant Runtime as RuntimeSettingsService
    participant Bus as SystemBus
    participant DPH as DphPublisher
    participant Comm as 通信接入
    participant Radar as 雷达 / test_comm

    UI->>API: PUT /api/runtime-settings full DTO
    API->>Runtime: validate full settings
    Runtime->>Runtime: commit current snapshot
    Runtime->>Bus: publish DphParamsChanged
    Bus->>DPH: dispatch event
    DPH->>DPH: update cached params

    loop every 50ms
        DPH->>DPH: build DPH from cached params
        DPH->>Comm: sendTo dph target
        Comm->>Radar: UDP DPH
    end
```

关键原则：

- 当前代码要求 UI 提交完整 `RuntimeSettings` DTO；
- 后端持有完整有效快照；
- DPH publisher 不轮询总线；
- 50ms 周期只负责按最近参数发送。
- 局部参数更新属于后续扩展，不能在图中画成当前契约。

## 6. 任务激活与历史视图流程

```mermaid
sequenceDiagram
    participant UI as React Web
    participant API as WebApiController
    participant Task as TaskService
    participant Device as DeviceRegistry
    participant Track as TrackDisplayManager
    participant Store as DataStore

    UI->>API: activate draft task
    API->>Task: activate(taskId)
    Task->>Task: reject when another task is active
    Task->>Device: validate bound controllable radar
    Task->>Store: persist Active status
    Task-->>API: authoritative task DTO
    API-->>UI: authoritative task DTO
    Track->>Task: read active task context
    Track->>Track: clear live cache when context changes

    UI->>API: view completed/archived task
    API->>Store: query tracks/events/logs by taskId
    Store-->>API: bounded latest history
    API-->>UI: read-only history DTOs
```

固定行为：

- 同一时刻最多一个活动任务；新任务不得静默完成旧任务，结束任务必须显式调用 `complete`；
- 活动任务由后端持久化，core/UI 重启后恢复，不要求用户每次重新创建；
- 任务绑定设备后，航迹、事件和日志按 `taskId + deviceId` 自动归属，不再逐类手工绑定；
- 查看历史记录不改变活动任务，历史航迹和日志只读；
- UI 地图、PPI、表格按当前活动任务或当前历史视图过滤。

## 7. 设备台账加载流程

```mermaid
sequenceDiagram
    participant UI as React Web
    participant API as WebApiController
    participant Device as DeviceRegistry
    participant Store as DataStore
    participant Config as endpoints.json

    UI->>API: GET /api/devices
    API->>Device: list devices
    Device->>Store: load DeviceInfo
    Device->>Config: resolve endpoint binding
    Device-->>API: DeviceInfo + runtime state
    API-->>UI: fixed Device DTO
```

关键原则：

- 前端加载后端设备台账；
- 通信端点仍由配置驱动；
- 设备和端点通过 binding 关联。
