# 06 - 航迹模型契约与字段映射

> 状态：历史迁移草案。总线包设计已由 `08-现有航迹链路审计与统一入口.md` 修订为唯一 `DataPacket + command + variant payload`；本文继续作为航迹字段语义依据。  
> 范围：雷达航迹从协议接收到识别后分发的核心数据链路。  
> 核心决定：主干只流转一个轻量 `TrackPacket`，不再设计识别前后两套航迹结构。

## 1. 目标链路

```text
厂家原始字节
  -> InputProtocolAdapter
       `-> 内部临时 GeneralPackage
  -> TrackPacket（recognitionStatus = Pending）
  -> RecognitionModule 原地处理/移动返回
  -> TrackPacket（recognitionStatus = Completed）
  -> SystemBus（只发布一次，只读共享）
       |-> TrackDisplayManager
       |-> TrackStorage
       `-> 后续业务消费者
```

固定规则：

1. `GeneralPackage` 只描述厂家协议布局，只存在于输入适配器内部；
2. 航迹主干从适配输出到各消费者始终使用同一个 `TrackPacket`；
3. 识别模块不创建另一套航迹模型，只填写同一包内的识别字段；
4. `TrackPacket` 只有完成识别后才能发布到 `SystemBus`；
5. 总线只发布一次，并以 `shared_ptr<const TrackPacket>` 共享只读数据；
6. `TrackDisplayUpdate` 是 Web 表现层输出，不属于航迹主干；
7. 当前协议一包只有一条 `TargetType`，V1 不预先增加 Batch；
8. 不把控制、日志、配置等异构消息重新塞入这个航迹包。

## 2. 为什么不继续使用旧 DataPacket

现有 `DataPacket` 是固定大小的万能容器：

```cpp
union PayloadUnion {
    uint8_t rawData[4096];
    GeneralPackage generalPackage;
};
```

在当前 `#pragma pack(1)` 布局下，`sizeof(DataPacket)` 约为 4448 字节。即使只传一条航迹，也携带：

- 4096 字节固定 payload；
- 256 字节错误描述；
- 源文件和行号；
- UI dispatchTarget；
- 与航迹无关的错误、日志和通用路由字段。

问题不只是大小，还包括：

- 新消息需要扩展 payloadType 和 union；
- 厂家 `GeneralPackage` 穿透到内部；
- 按值入队时复制整个固定缓冲；
- 错误、控制、航迹被强制使用同一结构；
- 类型安全依赖人工检查 payloadType；
- `BusEnvelope::shared_ptr<const void>` 又增加了第二套无类型载荷。

V1 不重写所有消息系统，只让新的航迹主干停止使用旧 `DataPacket`。旧包继续服务尚未迁移的控制和错误消息。

## 3. GeneralPackage 的位置

`GeneralPackage` 仍然保留，因为它负责：

- 定义硬件协议字段和字节偏移；
- 配合 `static_assert` 锁定结构体大小；
- 将完整 UDP 数据报安全解码；
- 为厂家输入适配器提供字段来源。

对外接口直接返回 `TrackPacket`：

```cpp
std::optional<TrackPacket>
InputProtocolAdapter::decode(QByteArrayView bytes,
                             const TrackSourceContext& source);
```

适配器内部可以使用临时协议对象：

```cpp
GeneralPackage packet{};
memcpy(&packet, bytes.data(), sizeof(packet));
return mapToTrackPacket(packet, source);
```

`GeneralPackage` 不进入 SystemBus、识别、显示、存储和 Web。

## 4. 唯一航迹包 TrackPacket

以下为 V1 语义草案。实现时保持一个结构体，不要求再拆分 Header/Payload 子结构。

```cpp
enum class RecognitionStatus : uint8_t {
    Pending = 0,
    Completed,
    Failed
};

enum class RecognitionType : uint8_t {
    Unknown = 0
};

struct TrackPacket {
    // 契约与链路
    uint16_t schemaVersion = 1;
    uint64_t traceId = 0;

    // 来源与归属
    QString endpointId;
    QString deviceId;
    QString taskId;

    // 时间与景幅
    qint64 receivedAtMs = 0;
    qint64 ingressSteadyNs = 0;
    qint64 normalizedSteadyNs = 0;
    qint64 recognizedSteadyNs = 0;
    uint32_t sceneNumber = 0;

    // 航迹标识与运动学
    uint32_t trackId = 0;
    double rangeM = 0;
    double azimuthRad = 0;
    double elevationRad = 0;
    double radialSpeedMps = 0;
    double rcs = 0;
    double altitudeM = 0;
    double xM = 0;
    double yM = 0;
    double zM = 0;
    double vxMps = 0;
    double vyMps = 0;
    double vzMps = 0;

    // 识别结果
    RecognitionStatus recognitionStatus = RecognitionStatus::Pending;
    RecognitionType recognitionType = RecognitionType::Unknown;
};
```

### 4.1 状态含义

| 状态 | 含义 | 能否发布到航迹总线 |
| --- | --- | --- |
| `Pending` | 协议已适配，尚未经过识别模块 | 否 |
| `Completed` | 识别流程完成；结果可以仍为 Unknown | 是 |
| `Failed` | 识别执行失败 | 默认否，记录错误和计数 |

`Unknown` 表示识别正常完成但没有得到已知分类，不等同于识别失败。

### 4.2 V1 不预埋的字段

当前没有正式识别算法契约，因此暂不增加：

- 无人机、鸟类、车辆等分类枚举；
- confidence；
- 模型名称和版本；
- 厂家识别码；
- 引导、追踪、校准状态；
- 显示颜色和交互状态。

真实识别模块确认需要后，再在识别结果区域追加字段并提升 `schemaVersion`。

## 5. 生命周期与复制策略

主干采用移动语义，不能在每一层深拷贝：

```cpp
auto packet = adapter.decode(bytes, source);
if (!packet)
    return;

recognition.process(*packet);  // 填写 recognition 字段
if (packet->recognitionStatus != RecognitionStatus::Completed)
    return;

auto published = std::make_shared<const TrackPacket>(std::move(*packet));
trackBus.publish(std::move(published));
```

生命周期：

1. UDP 字节由通信层持有；
2. `GeneralPackage` 是适配器栈上临时对象；
3. 适配器创建一次 `TrackPacket`；
4. 识别模块处理同一个包；
5. 发布前移动进 `shared_ptr<const TrackPacket>`；
6. 显示、存储等消费者共享读取，不复制整包。

发布后必须只读。任何消费者需要的派生数据由消费者自己持有，不能修改权威航迹包。

## 6. 字段映射

### 6.1 上下文映射

| TrackPacket 字段 | 当前来源 | 规则 |
| --- | --- | --- |
| `schemaVersion` | 新契约 | V1 固定为 1 |
| `traceId` | 当前 `m_traceSequence` | 进程内递增，仅用于链路追踪 |
| `endpointId` | `CommunicationManager::dataReceived` | 原值，仅用于来源和诊断 |
| `deviceId` | `DeviceRegistry::cachedDeviceIdForEndpoint()` | 必须由 endpoint 映射，不得冒用 endpointId |
| `taskId` | `TaskService::resolveTaskIdForDevice()` | 无活动任务时允许为空 |
| `receivedAtMs` | `UdpEndpoint` 捕获的 `receivedMs` | Unix epoch ms |
| `ingressSteadyNs` | `receivedSteadyNs` | 仅进程内时延统计 |
| `normalizedSteadyNs` | 输入适配完成时间 | 单调时钟 ns |
| `recognizedSteadyNs` | 识别完成时间 | 单调时钟 ns |
| `sceneNumber` | `DataPackageHeader::F_UI_Scene_Num` | 原值 |

### 6.2 运动学字段映射

| TrackPacket 字段 | TargetType 来源 | 单位/转换 |
| --- | --- | --- |
| `trackId` | `TargetID` | uint32 原值 |
| `rangeM` | `Range` | m，原值 |
| `azimuthRad` | `Azimuth` | rad，原值 |
| `elevationRad` | `Elevation` | rad，原值 |
| `radialSpeedMps` | `RadialSpeed` | m/s，原值 |
| `rcs` | `RCS` | 原值，单位待协议确认 |
| `altitudeM` | `Altitude` | m，基准待确认 |
| `xM/yM/zM` | `x/y/z` | m，坐标系待确认 |
| `vxMps/vyMps/vzMps` | `vx/vy/vz` | m/s，坐标系待确认 |

### 6.3 与现有 TrackPoint 映射

| TrackPacket | 现有 TrackPoint |
| --- | --- |
| `traceId` | `traceId` |
| `receivedAtMs` | `timestampMs` |
| `ingressSteadyNs` | `ingressSteadyNs` |
| `normalizedSteadyNs` | `normalizedSteadyNs` |
| `deviceId/taskId` | `deviceId/taskId` |
| `sceneNumber` | `sceneNumber` |
| `trackId` | `trackId` |
| `rangeM` | `range` |
| `azimuthRad/elevationRad` | `azimuth/elevation` |
| `radialSpeedMps` | `radialSpeed` |
| `rcs/altitudeM` | `rcs/altitude` |
| `xM/yM/zM` | `x/y/z` |

`displayReadySteadyNs` 由显示层产生，不进入 `TrackPacket`。

## 7. Header 和 host_computer 其他字段

后续确实需要的协议字段按用途处理：

| 类型 | 处理方式 |
| --- | --- |
| 只用于包校验、消息分类 | 留在 InputProtocolAdapter 内 |
| 有跨厂家稳定业务含义 | 确认语义后增加到 TrackPacket |
| 只服务当前厂家预处理 | 留在厂家适配层 |
| 没有明确消费者 | 暂不加入 |

当前暂不进入 V1 的字段：

| 协议字段 | 原因 |
| --- | --- |
| `wave_row/wave_col/wave` | 当前无消费者 |
| `CourseAngle/PitchAngle` | 名称与注释冲突，单位不明 |
| `TargetSize` | 单位和消费者不明 |
| `cluster_id/count` | 语义和消费者不明 |
| `time_accumulate_` | 时间单位和起点不明 |
| `Track_recognition_mark` | 厂家编码表不明，不能充当系统权威识别结果 |
| `Coming_and_going_signs` | 编码不明 |
| `Point_position` | 当前显示自行生成 pointIndex |
| `Actual_or_supplementary_points` | 编码不明 |
| `Extrapolation_frequency` | 当前无消费者 |
| `Update_Flag` | 有效性规则尚未确认 |
| `host_computer::view` | 与 header sceneNumber 关系不明 |

这些字段继续保留在原始 `GeneralPackage` 中，并未破坏协议兼容性。

## 8. 总线设计

新航迹消息不再使用旧 `DataPacket` 和 `BusEnvelope::shared_ptr<const void>`。

航迹通道最小接口：

```cpp
using TrackPacketPtr = std::shared_ptr<const TrackPacket>;

bool publish(TrackPacketPtr packet);
SubscriptionId subscribe(TrackCallback callback);
```

最小约束：

- 只接受 `recognitionStatus == Completed`；
- 队列有界；
- publish 失败返回 false 并计数；
- 回调只接收 `TrackPacketPtr`；
- 不做 payloadType、void 指针和 rawData 解包；
- 不为每个订阅者复制 TrackPacket。

是否直接扩展现有 `SystemBus`，还是增加一条类型化航迹通道，在编码前通过现有实现细节评审决定；对消费者暴露的契约必须保持上述类型安全接口。

## 9. 显示和存储边界

### 9.1 显示

`TrackDisplayManager` 输入 `TrackPacketPtr`，输出自己的 `TrackDisplayUpdate`：

```text
TrackPacket（权威航迹）
  -> 显示缓存和字段裁剪
  -> 初始 snapshot / 增量 delta
  -> WebBridge / React
```

当前窗口 diff 和 JSON 构建是 Web 输出成本，与航迹主干是否使用一个包无关；稳态不再重复复制和发送未变化点。

### 9.2 存储

`TrackStorage` 输入同一个 `TrackPacketPtr`，提取数据库列并批量写入。不得保存 `TrackDisplayUpdate`。

当前 tracks 表尚未保存：

- `vx/vy/vz`；
- `rcs`；
- 识别结果。

是否扩表在存储迁移阶段决定，本设计不立即修改数据库。

## 10. 标识、单位与坐标

实时航迹 key：

```text
(deviceId, trackId)
```

历史归属 key：

```text
(taskId, deviceId, trackId)
```

核心单位固定为：

| 量 | 单位 |
| --- | --- |
| 距离、坐标、高度 | m |
| 方位角、俯仰角 | rad |
| 速度 | m/s |
| 墙上时间 | ms |
| 单调时间 | ns |

当前尚未确认 `x/y/z` 坐标系、轴方向及 `Altitude` 高度基准，因此 V1 只无损映射数值，不执行坐标变换或跨设备融合。

## 11. 迁移顺序

1. 为 `sizeof(DataPacket)`、协议字段映射和单位增加基线测试；
2. 新增最小 `TrackPacket`；
3. 提取 `GeneralPackage -> TrackPacket` 纯转换函数及单元测试；
4. 实现同步透传识别，在同一个包中把状态改为 Completed/Unknown；
5. 增加类型化航迹发布接口；
6. 旁路发布新 `TrackPacket`，旧显示和存储路径暂时不动；
7. 对照旧 `TrackPoint`、数据库和 Web 数值；
8. 显示改为消费 `TrackPacketPtr`；
9. 存储改为消费 `TrackPacketPtr`；
10. 基线和时延测试通过后删除 `trackPointReady`；
11. 最后停止向旧总线发布完整 `GeneralPackage`。

每次只替换一个边界，不同时重写 Processor、总线、显示、存储和 Web。

## 12. 实施门禁

出现以下情况时停止编码并先修正文档：

- 新包再次出现固定大块 rawData；
- 新包加入错误描述、源文件等非航迹字段；
- 发布后仍允许消费者修改包；
- 一个消费者要求把显示或业务状态塞回 TrackPacket；
- 厂家结构体进入识别、显示或存储接口；
- 新总线仍使用 `shared_ptr<const void>`；
- 为尚不存在的设备或算法增加抽象；
- 新旧路径数值不一致；
- CTest、前端构建或 P95/P99 基线退化。

## 13. 待确认协议问题

编码前仍需逐步确认：

1. `x/y/z` 的坐标系、轴方向和原点；
2. `Altitude` 的高度基准以及它与 `z` 的关系；
3. `CourseAngle/PitchAngle` 的真实含义和单位；
4. `time_accumulate_` 的单位和起点；
5. 出现/消失、实测/补点、更新标志的编码；
6. `Track_recognition_mark` 的编码表；
7. `TargetID` 在设备重启、任务切换和多阵面之间的唯一性；
8. `vx/vy/vz` 与 `RadialSpeed` 的符号及坐标约定。
