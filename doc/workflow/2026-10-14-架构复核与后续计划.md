# 2026-10-14 架构复核与后续计划

当前已建立可工作的单雷达闭环，架构方向没有回到中央总线；整体模块尚未全部完成。
主要缺口在系统状态、归档故障可见性、接入错误事实和历史查询。不能因实时显示正常就标记整个架构验收通过。

依据为 AGENTS.md、架构 09、现行状态/事件/归档合同与当前源码；不以旧 05～08 链路作为实现依据。
本轮静态追踪 UDP/协议/Producer/Topic、Lane/WebReader、存储归档、任务/采集异步编排和 Command owner。
负载范围为当前单机、单完整雷达、四阵面、浏览器实时显示与 SQLite 同时归档。
未逐行审查第三方依赖、地图 SDK、启动器全部 Win32 分支，也未执行编译、测试、吞吐或数据库故障注入。

用户最新反馈：航迹显示正常，目前暂时没有问题；不把此反馈解释为归档、停机排空、慢数据库或部署全量验收。
联试工具仍每 200 ms 最多处理 32 行，忽略 CSV Time；本轮不修改发送节奏或增加显示插值。

## 已核实的架构边界

- 航迹：UdpEndpoint → DcmpProtocolAdapter → TrackIngressProducer/TrackPublisher → HistoryTopic<TrackPacket>。
- Web/归档各用独立 cursor 和固定 ScratchBuffer，Topic 预分配槽位；不建立每 Consumer 消息队列。
- Doorbell 只报告水位，ExecutionLane 合并 pending 位；消费者工作在各自既有执行线程。
- 控制：HTTP/UI → ApplicationController → DeviceController → 临时编码 → 同一 UDP 端点。
- DeviceController 唯一持有控制快照；0x0001 为 50 ms 双心跳门控，0xFFFF 由本地采集切换触发，无 ACK/重试 FIFO。
- 运行期 HTTP 异步调用存储，最多 16 在途、32 连接、写请求互斥；同步屏障仅用于启动/关停。
- 本次定向检查未发现新 DataPacket、SystemBus、跨类型 Broker 或第二条正式显示/落库/控制发送路径。

## 审查发现（按处理优先级）

### 1. P1：归档失败或缺口在运行中缺少可见闭环

证据：core/archive/ArchiveReader.cpp:150～186；core/app/StorageRuntime.cpp:306～349。
提交失败只增加计数并保留 cursor；gap 计数后继续归档仍驻留的窗口。提交失败计数没有运行期消费方，gap 仅在关停判定是否正常退出。
当 SQLite 暂时不可写，显示仍可继续；若故障持续到 RingBuffer 覆盖，用户可能在运行时不知道归档已经缺失。

最小修复：由存储职责报告失败/恢复和精确 gap，交系统状态 Owner 更新当前降级位，并通过唯一 SystemEventPublisher 发布限频事实。
特别处理 EventTopic 自消费：不能每次失败都新增一条同类失败事件，形成失败→事件→失败循环。
架构 09 已明确此阶段暂留指标、等待事件限频策略，因此这是已知未完成闭环，不应夸大为已违反临时迁移约定。

### 2. P2：SystemState 已有字段合同，但没有实际写入 Owner 和 Web 出口

证据：core/datadomain/CoreDataDomain.h:84～91；core/app/ApplicationRuntime.h；core/web/StateWebSocketService.cpp:96 起。
全仓 systemState 搜索只有访问器/字段，RuntimeStateGate 校验没有运行期调用；当前 WebReader 只读取 DeviceState。
启动完成、Web/归档降级及恢复不能形成权威系统快照。前端 WebSocket 已连接只证明浏览器链路成立。

最小修复：按运行状态合同补一个具体 SystemStateOwner，组合根和存储分别报告真实事实；使用现有 LatestState 和 Lane。
不得由该 Owner 读取航迹、执行命令、接管数据库或创建新调度中心。
WebReady 的 Core 边界与外部 Node 服务就绪不能混称；实现前明确现有接口字段及可观测范围。

### 3. P2：设备 connectionState 只在开始采集时赋值，此后可能陈旧

证据：core/control/DeviceController.cpp:84～214、398～399。
采集开始时按当时心跳写 Connected/Disconnected；acceptHeartbeat 与 checkHeartbeatDeadlines 只更新心跳、阵面和位姿，
没有同步更新 devices 中的 connectionState。在线开始后两路心跳超时，可能出现心跳灰色但内部 connectionState 仍为 Connected；反向恢复同理。
当前 Web 映射主要使用 operatingState，可能暂时掩盖这一不一致，后续读者不能信赖该字段。

最小修复：先固定 DP/SP 一路在线、双路迟到/超时的聚合规则，再由现有 DeviceController 在同次完整状态替换中同步更新。
通信状态与本地 Collecting 必须正交，不因心跳丢失伪造停止采集或设备 ACK。

### 4. P2：接入拒绝事件有码和显示映射，但缺少真实发布路径

证据：core/app/ApplicationRuntime.cpp:45～69；core/producer/TrackIngressProducer.cpp:71 起；core/model/SystemEvent.h:79～81。
协议非法帧和航迹拒绝主要累计终端诊断；DeviceMalformedFrame、TrackPublishRejected、SystemTopicSequenceGap
已经登记且有 Web 文案，但对应接入/归档场景没有发布这些事件。
终端隐藏的部署环境中，操作员无法从活动日志区分坏帧、未绑定会话、字段门禁或历史缺口。

最小修复：在知道失败原因的唯一 owner 发布有界、限频的已发生事实，区分正常未采集拒绝与真正异常；复用已有事件码。
不把逐包错误转为逐包日志，不增加字符串热路径或平行日志数据库。

## 后续工作顺序

1. **系统状态最小闭环**：固定就绪位的真实边界，补 SystemStateOwner，接入生命周期与现有 WebReader/Lane。
   验收：启动成功/失败、进入停止、状态重连快照均可解释；不重复保存 Device/Task 状态，不引入新线程。
2. **归档降级与恢复**：明确失败/恢复限频、gap 记录和 EventTopic 自消费规则，接入 SystemState 和统一事件链。
   验收：数据库不可写期间实时显示/控制继续，恢复后状态解除；已覆盖的缺口不能被“恢复成功”抹去。
3. **设备通信状态与接入错误**：修正第 3 项，补第 4 项的已登记事件，移除定位结束后确认为冗余的临时诊断。
   验收：单/双心跳迟到、超时、恢复与 connectionState 一致；坏帧风暴下日志数量有界。
4. **历史读取闭环**：先日志检索，再航迹查询/回放；查询共享存储线程但必须有界分页，不能重新阻塞主线程。
   验收：只展示真实数据库记录，身份/单位/时间合同一致；实时链与历史读取互不创建第二份内存历史。
5. **按真实业务再推进**：识别算法、插件、独立报警、多设备/光电等，先补输入/输出合同和用户授权。

以上是排期，不是本轮已实施功能。下一轮建议只推进第 1 步；本轮不自动开始写 SystemStateOwner。
编译与运行验收由用户执行；只有用户明确要求才新增 Python 测试程序。
