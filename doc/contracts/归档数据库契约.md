# SQLite 归档与配置数据库契约

> 状态：七表 Schema 12 实施合同
> Schema 版本：12
> 日期：2026-09-02  
> 架构依据：`doc/architecture/新架构4.png`、`doc/architecture/09-共享强类型数据域与游标读取模型.md`

## 1. 目的与边界

本合同定义雷达上位机第一版 SQLite 数据库的表结构、字段语义、关系、索引、事务和保留规则。数据库同时承担：

- 设备及通信配置的唯一持久化真源；
- 任务与每次采集会话的生命周期记录；
- `ArchiveReader` 对 `TrackTopic` 和 `EventTopic` 的历史归档；
- 后端进程启动、正常退出和异常中断的诊断记录。

数据库不是 `CoreDataDomain`，也不改变共享强类型数据域模型：

```text
TrackTopic / EventTopic
        ^
        | readAfter(committedCursor, ScratchBuffer)
        |
ArchiveReader
        |
        | 同步批量事务
        v
SqliteArchiveRepository
```

正常停机须先关闭实时输入，再由同一 `ArchiveReader` 将停机时 Track/Event 的 Topic 水位分别追到已提交 cursor；
归档失败或检测到 retention gap 时不得将 `application_runs` 标记为正常退出，数据库连接仍应释放并保留失败诊断。

数据库明确不承担 Topic、Doorbell、ExecutionLane、协议解析、航迹识别、Command dispatch、当前显示状态、
`DataPacket/variant` 存储或原始 UDP 帧录制。配置修改必须经过 Qt 后端配置服务，React UI 不直接执行 SQL。

## 2. 已确认业务参数

1. 50 ms 是旧版厂家大包头周期，不构成新协议发送周期约束，更不是单条航迹固定频率；容量评估必须使用真实峰值航迹条数，
   不得按“每 50 ms 一条航迹”推断或降采样。
2. `track_observations` 按接收时间保留一周。
3. `system_events` 的 Info、Warning、Error、Fault、Alarm 第一版统一保留一周。
4. 当前不设置数据库文件容量上限，但必须暴露文件大小、WAL 大小、提交耗时和失败次数指标。
5. 当前没有“断电也不能丢失”的事实，第一版使用 `synchronous=NORMAL` 与批量事务。
6. 删除任务采用软删除；任务、采集会话和配置历史不得因 UI 删除操作级联物理删除。
7. 一项任务可以多次启动和停止，同一次启动形成一个独立 `collection_sessions` 记录。

## 3. 七张表与关系

当前 Schema 12 只创建以下七张业务表：

1. `application_runs`：整个后端进程的一次运行生命周期；
2. `devices`：版本化设备台账、逐阵面安装姿态、通信端点和厂家配置；
3. `control_templates`：可复用的雷达控制参数模板；
4. `tasks`：任务元数据、模板来源与创建时复制的参数快照；
5. `collection_sessions`：某任务使用某设备的一次实际接收时段；
6. `track_observations`：从 `HistoryTopic<TrackPacket>` 归档的航迹事实；
7. `system_events`：从 `EventTopic<SystemEvent>` 归档的事件事实，包含归档 sequence gap。

```text
application_runs 1 ─── N collection_sessions
application_runs 1 ─── N track_observations
application_runs 1 ─── N system_events

tasks             1 ─── N collection_sessions
control_templates 1 ─── N tasks（仅记录来源；任务参数使用独立快照）
devices(revision) 1 ─── N collection_sessions
collection_sessions 1 ─── N track_observations

system_events 可选关联 task / device revision / collection session / track / endpoint
```

不创建 `schema_migrations`，Schema 版本只使用 SQLite `PRAGMA user_version`。不创建独立 `endpoints` 表，通信端点
属于某个设备配置版本。不创建 `archive_gaps` 表，gap 以已登记的 `SystemTopicSequenceGap` 事件写入
`system_events`。

## 4. 数据库文件与初始化

新数据库初始化必须在通信接收和 ArchiveReader 启动前完成，并在一个事务内创建全部对象。数据库标识固定为：

```sql
PRAGMA application_id = 1312900178; -- 0x4E414452, "NADR"
PRAGMA user_version = 11;
```

打开写连接后必须设置：

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 1000;
PRAGMA temp_store = MEMORY;
PRAGMA auto_vacuum = INCREMENTAL;
```

约束如下：

- SQLite 写连接只属于共享存储 ExecutionLane 所在线程，不得跨线程使用 `QSqlDatabase`；
- Web、历史查询和导出线程各自创建只读连接，并设置 `PRAGMA query_only=ON`；
- `application_id` 不匹配时拒绝打开，不能把未知 SQLite 文件当成本项目数据库；
- `user_version` 高于程序支持版本时拒绝打开；低于当前版本时，只能在实时链启动前执行受控升级；
- Schema 创建或升级失败必须整体回滚并禁用归档，禁止在半迁移结构上继续写入；
- 不使用 `STRICT`、触发器、存储过程或实时链运行期间的 Schema 修改；受控升级只允许在通信入口启动前完成。
- `user_version=1` 升级至 2 时只增加 `track_observations.pack_flag`，历史行按当时唯一语义补为 `1=存在`。
- `user_version=2` 升级至 3 时只增加 `track_observations.face_index`，旧单面阵历史补为0号阵面。
- `user_version=3` 升级至 4 时为设备台账增加阵面类型、作用距离和阵面参数，旧记录按单面阵补值。
- `user_version=4` 升级至 5 时一次性写入当前 `dcmp.dp.v1` 协议的单面阵、四面阵预置台账。预置项是可编辑、
  可软删除的初始配置；升级完成后不在每次启动时补写，因此用户删除后不会自动复活。
- `user_version=5` 升级至 6 时为任务增加雷达形态和设备阵面绑定字段，使任务驱动选择可跨重启恢复；不新增业务表。
- `user_version=6` 升级至 7 时只为当前 `dcmp.dp.v1` 设备追加不可变 revision，在
  `protocol_config_json.communication.targets` 中补齐 `dph` 和 `workmode` 具名发送目标；旧 revision 保留供历史事实引用。
- `user_version=7` 升级至 8 时，仅对两个内置 YHF-YZ-KU 台账中经纬高仍全为零的最新 revision
  追加默认部署位置 `118.65303°E, 31.93494°N, 63.9288 m`；用户已修改的位置绝不覆盖。
- `user_version=8` 升级至 9 时，把整机姿态迁移为逐阵面的 `heading/pitch/roll`，并保持历史 revision 可解释。
- `user_version=9` 升级至 10 时创建 `control_templates`，为 `tasks` 增加模板来源与控制参数快照，写入内置默认模板，
  并为全部既有任务补齐同一份独立快照。
- `user_version=10` 升级至 11 时为 `collection_sessions` 增加 `face_index`；旧会话按历史单面阵语义补为0号阵面。

## 5. 完整 Schema

### 5.1 `application_runs`：后端进程生命周期

```sql
CREATE TABLE application_runs (
    run_id                    INTEGER PRIMARY KEY,
    run_uuid                  BLOB    NOT NULL UNIQUE
                                      CHECK (length(run_uuid) = 16),
    started_utc_ms            INTEGER NOT NULL CHECK (started_utc_ms > 0),
    ended_utc_ms              INTEGER,
    abnormal_detected_utc_ms  INTEGER,
    application_version       TEXT    NOT NULL CHECK (length(application_version) > 0),
    schema_version            INTEGER NOT NULL CHECK (schema_version > 0),
    process_id                INTEGER CHECK (process_id IS NULL OR process_id > 0),
    shutdown_state            INTEGER NOT NULL DEFAULT 0
                                      CHECK (shutdown_state IN (0, 1, 2)),
    exit_code                 INTEGER,

    CHECK (ended_utc_ms IS NULL OR ended_utc_ms >= started_utc_ms),
    CHECK (abnormal_detected_utc_ms IS NULL
           OR abnormal_detected_utc_ms >= started_utc_ms),
    CHECK (
        (shutdown_state = 0 AND ended_utc_ms IS NULL
                            AND abnormal_detected_utc_ms IS NULL)
        OR
        (shutdown_state = 1 AND ended_utc_ms IS NOT NULL
                            AND abnormal_detected_utc_ms IS NULL)
        OR
        (shutdown_state = 2 AND ended_utc_ms IS NULL
                            AND abnormal_detected_utc_ms IS NOT NULL)
    )
);
```

| 字段                         | 含义                                              |
| -------------------------- | ----------------------------------------------- |
| `run_id`                   | 数据库本地整数主键，也是事实表解释 Topic sequence 和单调时间的运行域。     |
| `run_uuid`                 | 每次后端进程启动生成的 16 字节 UUID；跨重启稳定且不复用。               |
| `started_utc_ms`           | 本次进程开始初始化的 Unix epoch 毫秒。                       |
| `ended_utc_ms`             | 已知的正常退出时间；运行中或异常中断时为 NULL。                      |
| `abnormal_detected_utc_ms` | 下一次启动发现旧 run 未正常关闭的时间；不是推测的实际断电时间。              |
| `application_version`      | 产生本次数据的程序版本，用于还原事件码和历史行为。                       |
| `schema_version`           | 本 run 启动时使用的 `PRAGMA user_version` 快照。          |
| `process_id`               | 操作系统 PID，仅用于现场诊断，不作为身份或外键。                      |
| `shutdown_state`           | `0=Running/未闭合`、`1=Clean`、`2=AbnormalDetected`。 |
| `exit_code`                | 程序能够获得时保存退出码；崩溃或断电通常为 NULL。                     |

启动顺序固定为：先将历史上仍为 `shutdown_state=0` 的 run 标记为 `2` 并填写检测时间，再插入当前 run。正常停机
必须在停止 Producer、排空可提交归档并结束存储 Lane 后，把当前 run 更新为 `1`。应用通过单实例锁保证不会把
另一个仍在工作的进程误判为异常退出。

### 5.2 `devices`：版本化设备与通信配置

```sql
CREATE TABLE devices (
    device_revision_id       INTEGER PRIMARY KEY,
    device_uuid              BLOB    NOT NULL CHECK (length(device_uuid) = 16),
    revision                 INTEGER NOT NULL CHECK (revision > 0),
    display_name             TEXT    NOT NULL CHECK (length(display_name) > 0),
    manufacturer             TEXT    NOT NULL DEFAULT '',
    model                    TEXT    NOT NULL DEFAULT '',
    protocol_adapter_key     TEXT    NOT NULL DEFAULT '',
    array_type               INTEGER NOT NULL DEFAULT 1 CHECK (array_type IN (1, 4)),
    max_range_m              REAL    NOT NULL DEFAULT 5000.0 CHECK (max_range_m > 0.0),
    faces_json               TEXT    NOT NULL CHECK (length(faces_json) > 0),

    longitude_deg            REAL    NOT NULL
                                      CHECK (longitude_deg >= -180.0 AND longitude_deg <= 180.0),
    latitude_deg             REAL    NOT NULL
                                      CHECK (latitude_deg >= -90.0 AND latitude_deg <= 90.0),
    altitude_m               REAL    NOT NULL,

    endpoints_json           TEXT    NOT NULL CHECK (length(endpoints_json) > 0),
    protocol_config_json     TEXT    NOT NULL DEFAULT '{}',
    changed_utc_ms           INTEGER NOT NULL CHECK (changed_utc_ms > 0),
    changed_by               TEXT    NOT NULL DEFAULT '',
    change_reason            TEXT    NOT NULL DEFAULT '',
    is_deleted               INTEGER NOT NULL DEFAULT 0 CHECK (is_deleted IN (0, 1)),

    UNIQUE (device_uuid, revision)
);

CREATE INDEX idx_device_latest_revision
    ON devices(device_uuid, revision DESC);
```

| 字段                                                | 含义                                                 |
| ------------------------------------------------- | -------------------------------------------------- |
| `device_revision_id`                              | 某个不可变设备配置版本的数据库主键；采集会话引用此值。                        |
| `device_uuid`                                     | 完整雷达的跨重启稳定 UUID；同一整机的所有 revision 保持相同。             |
| `revision`                                        | 从 1 开始严格递增的配置修订号。                                  |
| `display_name`                                    | UI 展示名称，不参与航迹身份。                                   |
| `manufacturer` / `model`                          | 厂家和型号文本；未知时保存空字符串。                                 |
| `protocol_adapter_key`                            | Qt 后端选择厂家协议适配器的稳定登记键，不保存 C++ 类名；未配置协议时允许为空，但禁止开始采集。 |
| `array_type`                                      | `1=单面阵整机`、`4=四面阵整机`，不以任务内设备数量推断。                    |
| `max_range_m`                                     | UI覆盖绘制使用的最大斜距，单位m。                                  |
| `faces_json`                                      | 与阵面类型严格一致的 1 项或 4 项安装参数；编号连续覆盖 0 或 0～3。每项保存该阵面的 `headingDeg`、`pitchDeg`、`rollDeg`、`scanHalfAngleDeg` 和启用状态。四面阵以物理 1# 的实测航向为基准，其余阵面按顺时针每 90° 推导。 |
| `longitude_deg` / `latitude_deg`                  | 雷达 RFU 原点的经纬度，单位度。                                 |
| `altitude_m`                                      | 相对平均海平面 MSL 的海拔高度，单位 m；不是 WGS-84 椭球高。              |
| `endpoints_json`                                  | 本 revision 的完整通信端点数组，保存 endpoint 稳定键、角色、传输方式及地址端口。 |
| `protocol_config_json`                            | 仅保存当前厂家适配器真实需要、且已由配置服务验证的厂家参数。                     |
| `changed_utc_ms` / `changed_by` / `change_reason` | 谁在何时因何原因形成该 revision。                              |
| `is_deleted`                                      | 最新 revision 为 1 时表示设备已软删除；历史 revision 永不物理覆盖。      |

`devices` 采用追加 revision，而不是原地覆盖：新增设备写 revision 1；每次编辑复制上一版本并写 revision + 1；
删除设备也写一个完整 tombstone revision。当前配置定义为同一 `device_uuid` 下 revision 最大的记录。更新 revision
分配和新行插入必须处于同一写事务，唯一约束负责拒绝并发修订冲突。

`endpoints_json` 是设备配置中的有界复合字段，不是进程内万能消息。第一版固定为 UTF-8 JSON 数组，每项至少包含：

```json
{
  "endpointKey": "track-rx",
  "role": "track_receive",
  "transport": "udp",
  "localAddress": "0.0.0.0",
  "localPort": 3456,
  "remoteAddress": "127.0.0.1",
  "remotePort": 0
}
```

- `endpointKey` 在同一设备内稳定且唯一，配置改版时不得把旧键复用于不同角色；
- `role/transport` 使用配置合同登记值，第一版只实现真实使用的角色和 UDP；
- 不适用的远端地址和端口分别保存空字符串与 0；
- 配置服务必须在事务提交前校验 JSON 结构、IP/端口范围、endpointKey 唯一性及协议适配器参数；
- Schema 不调用 `json_valid()`，避免依赖 Qt 5.14.2 SQLite 驱动是否编译 JSON1；
- 密码、令牌和私钥不得以明文放入两个 JSON 字段，应保存系统凭据引用。普通 SQLite 集中配置并不等于加密。

采集开始时固定引用当时的 `device_revision_id`。运行期间产生新 revision 不得悄悄改变活动采集会话的安装姿态或
端点；需要立即生效的修改必须由 `DeviceController` 明确停止/重启设备并创建新采集会话。

### 5.3 `control_templates`：可复用控制参数来源

```sql
CREATE TABLE control_templates (
    template_id              INTEGER PRIMARY KEY,
    template_uuid            BLOB    NOT NULL UNIQUE CHECK (length(template_uuid) = 16),
    template_name            TEXT    NOT NULL UNIQUE CHECK (length(template_name) > 0),
    settings_json            TEXT    NOT NULL CHECK (length(settings_json) > 0),
    created_utc_ms           INTEGER NOT NULL CHECK (created_utc_ms > 0),
    updated_utc_ms           INTEGER NOT NULL CHECK (updated_utc_ms >= created_utc_ms),
    is_deleted               INTEGER NOT NULL DEFAULT 0 CHECK (is_deleted IN (0, 1))
);
```

`settings_json` 必须通过 `RadarControlSettings` 的强类型解析和范围校验；它是低频持久化边界，不能进入实时
Topic。V1 只提供数据库升级时写入的只读默认模板，不提前提供模板增删改接口。删除或后续修改模板不得改写
既有任务快照，因此任务只记录模板 UUID 来源，不建立会阻止模板演进的外键。

### 5.4 `tasks`：任务生命周期与软删除

```sql
CREATE TABLE tasks (
    task_id                  INTEGER PRIMARY KEY,
    task_uuid                BLOB    NOT NULL UNIQUE CHECK (length(task_uuid) = 16),
    task_name                TEXT    NOT NULL CHECK (length(task_name) > 0),
    operator_name            TEXT    NOT NULL DEFAULT '',
    description              TEXT    NOT NULL DEFAULT '',
    radar_array_type         INTEGER NOT NULL DEFAULT 1 CHECK (radar_array_type IN (1, 4)),
    device_bindings_json     TEXT    NOT NULL DEFAULT '[]'
                                      CHECK (length(device_bindings_json) > 0),
    source_template_uuid     BLOB,
    control_settings_json    TEXT,
    created_utc_ms           INTEGER NOT NULL CHECK (created_utc_ms > 0),
    updated_utc_ms           INTEGER NOT NULL CHECK (updated_utc_ms >= created_utc_ms),
    closed_utc_ms            INTEGER,
    archived_utc_ms          INTEGER CHECK (archived_utc_ms IS NULL OR archived_utc_ms >= closed_utc_ms),
    is_deleted               INTEGER NOT NULL DEFAULT 0 CHECK (is_deleted IN (0, 1)),
    deleted_utc_ms           INTEGER,
    deleted_by               TEXT    NOT NULL DEFAULT '',

    CHECK (closed_utc_ms IS NULL OR closed_utc_ms >= created_utc_ms),
    CHECK ((is_deleted = 0 AND deleted_utc_ms IS NULL)
           OR (is_deleted = 1 AND deleted_utc_ms IS NOT NULL)),
    CHECK (deleted_utc_ms IS NULL OR deleted_utc_ms >= created_utc_ms)
);

CREATE INDEX idx_task_created
    ON tasks(created_utc_ms DESC, task_id DESC);
CREATE INDEX idx_task_deleted
    ON tasks(is_deleted, created_utc_ms DESC, task_id DESC);
```

| 字段                                             | 含义                                       |
| ---------------------------------------------- | ---------------------------------------- |
| `task_id`                                      | 数据库本地任务主键。                               |
| `task_uuid`                                    | 创建任务时生成的跨重启稳定 UUID，对应运行时 `TaskId` 的持久身份。 |
| `task_name`                                    | 用户可见任务名称，不要求承担唯一身份。                      |
| `operator_name`                                | 创建或负责该任务的操作员展示名称。                        |
| `description`                                  | 用户填写的任务说明。                               |
| `radar_array_type`                             | `1=单面阵`、`4=四面阵`，用于约束任务可选择的设备类型。          |
| `device_bindings_json`                         | 稳定设备 UUID 与本次启用阵面位图的有界数组；不是进程内消息。       |
| `source_template_uuid`                         | 创建任务时所选模板的稳定 UUID，仅用于来源追溯。                   |
| `control_settings_json`                        | 创建时从模板复制的独立 `RadarControlSettings` 快照。              |
| `created_utc_ms` / `updated_utc_ms`            | 创建时间和最后一次元数据修改时间。                        |
| `closed_utc_ms`                                | 用户明确结束任务的时间；尚可继续采集时为 NULL。               |
| `archived_utc_ms`                              | 仅已完成且无活动采集的任务可设置；归档只改变任务展示状态，不搬移或删除历史事实。 |
| `is_deleted` / `deleted_utc_ms` / `deleted_by` | UI 软删除状态、删除时间和操作者。                       |

软删除只更新任务自身，不删除 `collection_sessions`、`track_observations` 或 `system_events`。已软删除任务默认不出现在
新任务列表，但历史查询和审计仍可通过 `task_uuid` 访问。任务是否正在采集由未结束的 `collection_sessions` 推导，
第一版不在此表重复保存容易失真的 `running` 布尔值。

Schema 10 由 SQLite `ALTER TABLE` 增加的两个任务列在物理定义上允许 NULL，以兼容受控升级；迁移事务会立即补齐所有
历史行，Repository 对加载和新建任务一律要求两列非空且能通过强类型校验。不得利用物理可空性创建无参数快照任务。

Schema 11 到 12 在启动期事务中给 `tasks` 增加 `archived_utc_ms`；已有已完成任务保持 NULL，待用户明确归档。
归档操作一次性写入该时间并更新 `updated_utc_ms`，重复归档、未完成任务和活动采集均拒绝。

### 5.5 `collection_sessions`：一次设备采集会话

```sql
CREATE TABLE collection_sessions (
    collection_session_id   INTEGER PRIMARY KEY,
    session_uuid            BLOB    NOT NULL UNIQUE CHECK (length(session_uuid) = 16),
    run_id                  INTEGER NOT NULL,
    task_id                 INTEGER NOT NULL,
    device_revision_id      INTEGER NOT NULL,
    endpoint_key            TEXT    NOT NULL CHECK (length(endpoint_key) > 0),
    face_index              INTEGER NOT NULL CHECK (face_index BETWEEN 0 AND 3),
    started_utc_ms          INTEGER NOT NULL CHECK (started_utc_ms > 0),
    stopped_utc_ms          INTEGER,
    stop_reason             INTEGER NOT NULL DEFAULT 0
                                      CHECK (stop_reason IN (0, 1, 2, 3, 4, 5)),

    FOREIGN KEY (run_id) REFERENCES application_runs(run_id),
    FOREIGN KEY (task_id) REFERENCES tasks(task_id),
    FOREIGN KEY (device_revision_id) REFERENCES devices(device_revision_id),
    UNIQUE (collection_session_id, run_id),
    CHECK (stopped_utc_ms IS NULL OR stopped_utc_ms >= started_utc_ms),
    CHECK (
        (stop_reason = 0 AND stopped_utc_ms IS NULL)
        OR
        (stop_reason IN (1, 2, 3, 4) AND stopped_utc_ms IS NOT NULL)
        OR
        (stop_reason = 5 AND stopped_utc_ms IS NULL)
    )
);

CREATE INDEX idx_session_task_time
    ON collection_sessions(task_id, started_utc_ms, collection_session_id);
CREATE INDEX idx_session_device_time
    ON collection_sessions(device_revision_id, started_utc_ms, collection_session_id);
CREATE INDEX idx_session_run
    ON collection_sessions(run_id, collection_session_id);
```

| 字段                                  | 含义                                                                                               |
| ----------------------------------- | ------------------------------------------------------------------------------------------------ |
| `collection_session_id`             | 数据库本地会话主键，事实表用它避免重复任务和设备配置。                                                                      |
| `session_uuid`                      | 每次开始接收、断线重连或重新采集时生成的 16 字节 UUID。                                                                 |
| `run_id`                            | 创建并拥有本会话的后端进程；第一版会话不跨进程续接。                                                                       |
| `task_id`                           | 本次采集所属任务。                                                                                        |
| `device_revision_id`                | 启动采集时冻结的设备配置版本。                                                                                  |
| `endpoint_key`                      | 本次接收使用的 endpointKey，必须存在于该设备 revision 的 `endpoints_json`。                                        |
| `face_index`                        | 本次会话唯一对应的物理阵面索引；四面阵各启用阵面分别建立会话。                                                          |
| `started_utc_ms` / `stopped_utc_ms` | 实际开始与已知停止接收的 UTC 毫秒；异常中断无法得知精确停止时间时保持 NULL。                                                      |
| `stop_reason`                       | `0=Running`、`1=UserStop`、`2=Disconnected`、`3=ProcessShutdown`、`4=Error`、`5=AbnormalProcessExit`。 |

运行时 `AcquisitionId` 只映射到本表主键或 `session_uuid`，其进程内整数值不得直接落库。一个任务可有多个会话，
同一任务的多台设备也分别创建会话。下一次启动发现异常 run 时，把该 run 下仍为 Running 的会话标记为
`AbnormalProcessExit`，但不伪造无法获知的 `stopped_utc_ms`。


| 字段组                       | 含义                                                        |
| ------------------------- | --------------------------------------------------------- |
| `observation_id`          | 本地自增式整数主键，用于稳定 keyset 分页；不使用 `AUTOINCREMENT`。             |
| `run_id + topic_sequence` | 当前进程内 TrackTopic 的唯一归档位置，用于批次重试幂等。                        |
| `collection_session_id`   | 同时确定任务、设备 revision 和接收 endpoint，不在每条航迹重复保存三者。             |
| `receive_time_utc_ms`     | 归档查询、回放排序和一周清理的主时间轴。                                      |
| `source_time_utc_ms`      | 厂家时钟已同步且 `HasSourceTimeUtcMs` 有效时保存，否则 NULL。              |
| `receive_time_steady_ns`  | 进程内单调接收时间，只能与同一 `run_id` 一起解释。                            |
| `source_sequence_u64`     | 厂家提供且 validity 有效时保存 8 字节大端无符号值，否则 NULL。                  |
| `trace_id_u64`            | 8 字节大端 `quint64` 位模式，用于诊断关联，不作为业务主键。                      |
| `quality`                 | `0=Good`、`1=Suspect`，与 `SampleQuality` 稳定数值一致。            |
| 航迹数值字段                    | 原样保存已通过门禁的 `TrackPacket` 权威极坐标、径向速度和厂家幅值。                 |
| `pack_flag`               | `1=存在`、`0=消亡`；归档与回放不得丢失消亡事实。                              |
| `face_index`              | 完整雷达内部阵面索引；单面阵为0，四面阵为0～3。                                 |
| `scan_sequence`           | `HasScanSequence` 有效时保存厂家 `quint32`，否则 NULL。              |
| 识别字段                      | 第一版只允许 `Completed(1)` 与 `Unknown(0)`；未来扩展必须先升级合同和 Schema。 |

`source_sequence_u64/trace_id_u64` 使用固定 8 字节大端 BLOB，避免 SQLite 有符号 INTEGER 不能覆盖完整 `quint64`
位域。`topic_sequence` 在可预见运行期内必须不超过 SQLite 正整数上限 `INT64_MAX`；超过时归档失败并形成 Fault，
不得转换成负数。

本表不保存 `EndpointId/DeviceId/TaskId/AcquisitionId` 的运行时数值，也不保存 RFU `x/y/z`、地图经纬高、Web DTO
或显示状态。回放通过 `collection_session_id -> device_revision_id` 获得当时的安装姿态，再从权威观测重新投影。
SQLite 不能可靠用 CHECK 拒绝所有 NaN/Inf；Repository 必须在绑定前再次验证全部浮点数为有限值。

| 字段组                       | 含义                                                         |
| ------------------------- | ---------------------------------------------------------- |
| `event_id`                | 本地事件主键和 keyset 分页的同时间戳次序。                                  |
| `run_id + topic_sequence` | 当前进程内 EventTopic 的唯一归档位置和重试幂等键。TrackTopic 有独立 sequence 空间。 |
| SampleMeta 字段             | 与航迹表采用相同 UTC、steady、source sequence、trace 和 quality 语义。    |
| 可选主体字段                    | 根据 `subject_flags` 解析；未置位时对应列必须为 NULL，而不是保存无效零值。           |
| `device_revision_id`      | 事件发生时绑定的设备配置版本；设备级事件没有活动采集也可以填写。                           |
| `endpoint_key`            | 事件关联端点时保存稳定键；必须由 Repository 根据当时设备配置解析。                    |
| `event_code`              | 已登记的跨版本稳定事件码。高 8 位必须与 `event_domain` 一致。                   |
| `event_domain`            | `1=Device`、`2=Track`、`3=System`、`4=Control`。               |
| `severity`                | `0=Info`、`1=Warning`、`2=Error`、`3=Fault`、`4=Alarm`。        |
| `argument0/argument1`     | 仅按事件码登记含义保存定长数值；无效时为 NULL。                                 |
| `message_template_id`     | 中文展示模板登记号；第一版代码要求为 0。                                      |

Repository 必须验证 `subject_flags` 与 NULL/非 NULL 列一致，并验证 `event_code` 高 8 位等于 `event_domain`。
`SystemTopicSequenceGap` 的两个参数保存丢失 sequence 闭区间，进入本表而不创建 `archive_gaps`。由于 gap 事件本身
仍需经过 EventTopic 和数据库提交，其持久化是尽力而为；立即且不依赖数据库的真实诊断来源是 ArchiveReader 的
gap 指标与限频运行日志，禁止为保证 gap 落库而重新引入第二条同步写路径。

事件正文不保存动态中文字符串。查询或导出时依据 `event_code/message_template_id/argument0/argument1` 格式化；
厂家原始文本如未来必须保留，应进入原始协议录制或明确有界的附件方案，不能无界加入事件热表。

## 6. 配置写入与读取合同

配置调用链固定为：

```text
React UI
  -> Qt Web/API Bridge
  -> DeviceConfigService（校验、鉴权、生成 revision）
  -> SqliteConfigRepository
  -> devices
  -> DeviceController（明确应用或重启）
```

- UI 只能提交业务配置命令，不能直接持有数据库路径、SQL 或写连接；
- 数据库提交成功后才能向 UI 返回保存成功；运行时应用失败不回滚历史 revision，而是返回失败 Result 并发布
  Control/System 事件，当前运行设备继续使用原 revision；
- 程序启动只从 `devices` 最新 revision 构建设备和 endpoint 注册表，不再同时读取 JSON/INI 作为第二真源；
- JSON/INI 只允许作为显式导入/导出格式，导入也必须经过同一配置校验和 revision 事务；
- 活动采集会话冻结 `device_revision_id`，保证历史航迹永远使用当时的经纬高和绝对姿态解释；
- 配置 API 返回 `device_uuid + revision`，客户端基于 revision 做乐观并发检查，过期编辑返回 Conflict。

## 7. 标识符与映射合同

`EndpointId/DeviceId/TaskId/AcquisitionId` 是进程内紧凑句柄，禁止直接作为跨重启身份。注册表映射如下：

| 运行时类型           | 持久身份                                         | 映射时机                    |
| --------------- | -------------------------------------------- | ----------------------- |
| `EndpointId`    | `device_uuid + revision + endpoint_key`      | 加载设备 revision 时建立。      |
| `DeviceId`      | `device_uuid`，运行时同时固定当前 `device_revision_id` | 配置加载或明确应用 revision 时建立。 |
| `TaskId`        | `task_uuid` / `task_id`                      | 创建或恢复任务时建立。             |
| `AcquisitionId` | `session_uuid` / `collection_session_id`     | 每次开始接收、重连或重新采集时建立。      |
| 当前进程            | `run_uuid` / `run_id`                        | Repository 启动时建立。       |

Repository 在启动和实体变化时维护 `CompactId -> local pk` 的有界缓存。Track/Event 批量热写不得逐行查询配置表，
也不得将数据库字符串反向塞入实时 `TrackPacket/SystemEvent`。

## 8. 批量事务与 cursor 合同

`appendTrackBatch` 与 `appendEventBatch` 使用各自 prepare 后复用的强类型 INSERT：

1. `BEGIN IMMEDIATE`；
2. 绑定 ArchiveReader 固定 ScratchBuffer 的前 `count` 条；
3. 任一记录映射、校验或 INSERT 失败，立即 `ROLLBACK`；
4. 全部 INSERT 成功后 `COMMIT`；
5. 只有 COMMIT 成功才返回 true；
6. ArchiveReader 收到 true 后才推进对应 Topic 的 committed cursor；
7. Repository 不保存 records 指针、不复制成内部 Queue，也不创建额外写线程。

初始固定批量上限：

- Track：256 条；
- Event：64 条。

`UNIQUE(run_id, topic_sequence)` 用于同一运行实例内批次重试幂等。发生唯一冲突时必须读取既有行并核对内容：
内容一致可视为已提交；内容不一致必须回滚并发布 Fault，不能使用 `INSERT OR IGNORE` 静默吞掉冲突。

WAL checkpoint 不在每批执行。存储 Lane 根据累计事务数或 WAL 大小执行 `PASSIVE` checkpoint；正常停止时执行
一次受限 checkpoint。磁盘同步、busy wait、维护删除和 checkpoint 都不得阻塞 Topic Producer。

## 9. 查询与索引合同

`receive_time_utc_ms` 是航迹与事件的归档、回放和保留主时间轴。`source_time_utc_ms` 只用于来源时间分析，
`receive_time_steady_ns` 只用于同一 run 内诊断。毫秒内可能存在多条记录，排序必须追加主键：

```text
ORDER BY receive_time_utc_ms, observation_id
ORDER BY receive_time_utc_ms, event_id
```

禁止对大结果集使用 OFFSET，统一使用 keyset cursor：

```sql
SELECT *
FROM track_observations
WHERE collection_session_id = :session_id
  AND ((receive_time_utc_ms > :last_time)
       OR (receive_time_utc_ms = :last_time AND observation_id > :last_id))
ORDER BY receive_time_utc_ms, observation_id
LIMIT :limit;
```

真实查询路径为：

- 任务回放：先查询该任务的 session 主键，再按 `idx_track_session_time` 分页读取；
- 单航迹回放：按 `collection_session_id + track_id + time` 读取；
- 设备历史：先把 `device_uuid` 的 revision 主键集合解析出来，再查询相关 session；
- 事件查询：按时间、域/事件码、严重度、任务或设备 revision 查询；
- 运行诊断：按 `application_runs.started_utc_ms` 和 run 主键查询相关 session/event。

第一版不为每个列预建索引。新增索引必须有真实 API 查询、`EXPLAIN QUERY PLAN` 和写放大测量依据。

## 10. 一周保留、软删除与磁盘故障

保留截止时间统一为：

```text
cutoffUtcMs = maintenanceNowUtcMs - 7 days
```

维护任务只按小批次执行：

1. 按 `receive_time_utc_ms, observation_id` 删除超过一周的 `track_observations`；
2. 按 `receive_time_utc_ms, event_id` 删除超过一周的全部等级 `system_events`；
3. 每批删除固定上限并提交，随后把执行权还给存储 Lane；
4. 使用 `incremental_vacuum` 分步回收空页，7×24 运行期间禁止全量 `VACUUM`；
5. `tasks/devices/application_runs/collection_sessions` 第一版不随一周事实数据自动删除；任务和设备删除只做软删除；
6. 当前不因文件大小主动删除未到期数据，但持续上报数据库和 WAL 字节数；
7. SQLite 返回 FULL、IOERR 或事务持续失败时，Repository 返回 false，ArchiveReader 不推进 cursor，实时显示继续；
8. Topic 后续覆盖造成的归档 gap 进入指标，并通过受限频的 `SystemTopicSequenceGap` 事件尽力归档。

一周清理不等于断电耐久承诺。`synchronous=NORMAL` 下已提交事务具备 SQLite/WAL 的常规崩溃恢复能力，但不声明
所有硬断电场景零丢失；若将来出现法规级事件，必须单独评审 `FULL`、专用 journal 或同步审计边界。

## 11. Schema 实施验收

1. 新库只含七张业务表，`application_id` 和 `user_version=11` 正确；首次初始化写入单面阵、四面阵台账和一条默认控制模板。
2. 每个任务都具有有效 `source_template_uuid` 和独立 `control_settings_json`；修改模板不反向改变既有任务快照。
   重复初始化不增殖预置项、不破坏已有数据，旧版本可受控迁移。
2. 上次未闭合 run 能在下次启动标记为 `AbnormalDetected`，正常退出记录真实结束时间。
3. 设备新增、编辑、软删除均产生连续 revision；旧采集会话始终解析到原设备 revision。
4. JSON/INI 不再作为运行配置第二真源；UI 修改必须经过配置服务、事务和 revision 冲突检查。
5. 一个任务可以产生多条 collection session；停止、重连和重新开始不会复用 `AcquisitionId/session_uuid`。
6. Track/Event 批次任一行失败时整批回滚，ArchiveReader cursor 不推进。
7. 重试同一 `(run_id, topic_sequence)` 不产生重复行，内容冲突明确失败。
8. `TrackPacket` 的单位、角度范围、速度符号、幅值和可选字段 NULL 语义与现行合同一致。
9. SystemEvent 的 flags、domain、eventCode、severity 和可选关联列通过映射门禁。
10. 按 session、TrackKey、时间和事件条件进行 keyset 查询时命中预期索引。
11. 一周清理采用小事务，不长时间占用存储 Lane；任务和设备软删除不级联清除事实。
12. 异常退出后 SQLite 可以恢复，未提交事务不可见；当前 `synchronous=NORMAL` 不宣称硬断电零丢失。
13. Track 256 条、Event 64 条的持续批量写入不阻塞 Producer；真实峰值容量以设备压测结果补充。
14. 数据库大小、WAL 大小、提交耗时、回滚、busy、FULL/IOERR 和 archive gap 均具有指标。

## 12. 逐表评审时仍需确认

以下内容不阻止 Schema 结构评审，但在实现对应 Repository/API 前必须由真实业务冻结：

1. `endpoints_json` 中现有全部端点角色、每个角色的本地/远端地址语义和是否允许一个角色多个实例；
2. `protocol_config_json` 中当前厂家协议真正需要持久化的参数清单；
3. 任务 `closed_utc_ms` 的操作语义，以及关闭后是否允许重新开启采集；
