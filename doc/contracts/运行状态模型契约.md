# DeviceState、TaskState 与 SystemState 运行状态模型契约

> 状态：设计冻结，尚未实现  
> 生效日期：2026-09-04  
> 适用范围：`CoreDataDomain` 中三个 `LatestState<T>`、各自唯一状态 Owner 与 Web 状态读取边界

## 1. 目的与架构位置

本文定义设备、任务和系统三类“当前完整状态”。它们由各自唯一 Owner 计算完成后，通过
`LatestState<T>::set(Sample<T>)` 原子替换；WebReader 收到只含 revision 的 Doorbell 后，再调用 `latest()`
取得完整快照。

```text
DeviceController  ── set ──> LatestState<DeviceState> ── latest ──> WebReader
TaskService       ── set ──> LatestState<TaskState>   ── latest ──> WebReader
SystemStateOwner  ── set ──> LatestState<SystemState> ── latest ──> WebReader
```

State 不是 Command、Event、数据库台账或指标集合：Command 表示尚未发生的意图并返回 `CommandResult`；State
表示读取瞬间仍然成立的完整当前事实；Event 表示已经发生且值得顺序观察或归档的事实；SQLite 保存配置、任务、
采集会话和历史，不由 State 复制。

## 2. 三项统一合同

1. 每次 `set()` 必须提交完整快照，禁止提交局部 patch。
2. revision 由 `LatestState<T>` 分配，不进入状态结构体，也不跨进程持久化。
3. State 的变化时间使用外层 `SampleMeta`；状态本体不重复保存“最后更新时间”。
4. 内部聚合状态的 `SampleMeta.endpointId` 为零，源序号和源时间 validity 位清零；若变化由某次命令触发，
   可以沿用该处理链的非零 `traceId`。
5. Doorbell 只报告 revision 水位，允许合并、重复或延迟，不传递 State 本体。
6. Consumer 即使错过多个 revision，也能仅凭一次 `latest()` 恢复完整当前状态。
7. 状态变化需要审计、告警或诊断时，Owner 另行发布 `SystemEvent`；不得依赖旧 State revision 充当历史。
8. State 更新属于低频控制链，可使用有界动态容器；容器必须受启动配置约束，禁止无界增长。

## 3. DeviceState

### 3.1 快照语义

`LatestState<DeviceState>` 保存当前进程所有已激活设备的完整运行时快照，而不是“最近发生变化的一台设备”。
设备 A 更新时，`DeviceController` 必须在自己的权威状态表中完成变更，然后重新生成包含全部设备的快照。

第一版不实现 `DeviceId -> LatestState<DeviceRuntimeState>` keyed registry，避免动态 State 生命周期、每设备
revision、每设备 Doorbell 和 Consumer 枚举协议。

### 3.2 建议类型

```cpp
enum class DeviceConnectionState : quint8
{
    Disabled = 0,
    Disconnected,
    Connecting,
    Connected,
    Degraded,
    Faulted
};

enum class DeviceOperatingState : quint8
{
    Idle = 0,
    Starting,
    Collecting,
    Stopping,
    Reconfiguring,
    Faulted
};

enum class DeviceStateFieldFlag : quint16
{
    None = 0,
    AcquisitionValid = 1U << 0,
    ActiveRequestValid = 1U << 1
};

struct DeviceRuntimeState
{
    AcquisitionId acquisitionId;
    quint64 activeRequestId;
    DeviceId deviceId;
    EndpointId primaryEndpointId;
    quint32 configurationRevision;
    quint32 currentFaultFlags;
    quint16 validity;
    DeviceConnectionState connectionState;
    DeviceOperatingState operatingState;
};

struct DeviceState
{
    QVector<DeviceRuntimeState> devices;
};
```

`DeviceRuntimeState` 是 DeviceState 的有界元素，不单独建立 Topic/State。引入该元素类型是表达多设备完整快照
所必需的复杂度；禁止继续为连接、采集、故障分别创建中间 DTO。

### 3.3 字段与不变量

| 字段 | 合同 |
| --- | --- |
| `deviceId` | 当前进程已激活设备 revision 的非零强类型句柄 |
| `primaryEndpointId` | 当前 revision 的主设备端点；设备禁用但配置有效时仍可非零 |
| `configurationRevision` | 当前实际生效的 SQLite 设备配置 revision，不是期望版本 |
| `connectionState` | 通信是否可用，不与设备工作状态合并为组合枚举 |
| `operatingState` | Idle、启停等待 ACK、采集、重配置或持续故障 |
| `acquisitionId` | 仅 `AcquisitionValid` 置位时有效；表示已确认采集会话 |
| `activeRequestId` | 仅 `ActiveRequestValid` 置位时有效；表示当前待 ACK 请求 |
| `currentFaultFlags` | 当前仍成立的有界故障位；历史故障进入 SystemEvent/SQLite |

1. `devices` 按 DeviceId 升序保存，DeviceId 在一个快照内唯一。
2. 数量不得超过启动配置的 `maxRuntimeDevices`；超限时 Owner 拒绝激活新设备，不能截断快照。
3. 所有无效可选字段必须清零。
4. `Collecting` 必须同时具有有效 AcquisitionId；`Starting` 尚未收到 ACK 时不得提前暴露采集会话。
5. `activeRequestId` 不保存 Command 内容或 FIFO。
6. 名称、厂家、型号、经纬高、姿态、端点 JSON 和协议配置仍由 DeviceConfigService/SQLite 持有。

### 3.4 唯一 Owner

`DeviceController` 是唯一写入者。UdpEndpoint、ProtocolAdapter、定时器和 UI 只能向控制流程报告输入，不得直接
调用 `set()`。启停等待 ACK、ACK 结果、连接变化、会话建立/结束、配置确认生效及持续故障变化触发完整快照；
单个非法报文或不改变当前状态的瞬时错误只发布 Event/指标。

## 4. TaskState

### 4.1 冻结业务约束

系统同一时刻最多有一个活动任务；一个任务可以同时使用多台设备。SQLite 可以保存多个历史或未删除任务，
但 `LatestState<TaskState>` 只表达当前活动任务的运行阶段，不复制任务列表和每台设备状态。

设备与 AcquisitionId 的当前关系已经存在于 DeviceState，禁止在 TaskState 再保存设备数组。WebReader 需要组合
展示时分别读取两个最新快照，不制造第三个长期状态。

### 4.2 建议类型

```cpp
enum class TaskPhase : quint8
{
    None = 0,
    Ready,
    Starting,
    Running,
    Stopping,
    Completed,
    Faulted
};

struct TaskState
{
    TaskId taskId;
    TaskPhase phase = TaskPhase::None;
};
```

第一版不增加设备列表、任务名称、操作员、开始时间或采集计数。名称和操作员来自任务台账；采集明细来自
DeviceState 和 SQLite；状态更新时间来自 SampleMeta。

### 4.3 不变量与转换

- `None` 必须搭配零 TaskId；其他阶段必须搭配非零且可由 TaskService 解析的 TaskId。
- 创建任务只写 SQLite，不自动使它成为活动任务；选择后进入 `Ready`。
- 发起至少一台设备启动后进入 `Starting`；至少一个启动 ACK 成功且会话提交成功后进入 `Running`。
- 停止流程开始后进入 `Stopping`；全部相关会话收口后进入 `Completed`。
- 无法继续任务的故障进入 `Faulted`；单台设备失败但其他设备仍满足任务时允许保持 `Running` 并发布 Event。
- 从 `Completed/Faulted` 清除当前任务后回到 `None`，不得复用旧 AcquisitionId。

`TaskService` 是唯一写入者。ApplicationController 只编排 DeviceController 与 TaskService 的调用顺序，不能直接
修改 TaskState。

## 5. SystemState

### 5.1 快照语义与建议类型

`LatestState<SystemState>` 表示后端进程当前生命周期、总体健康度和关键服务就绪情况，不聚合设备、任务、历史
事件、统计计数或业务命令。

```cpp
enum class ApplicationPhase : quint8
{
    Starting = 0,
    Ready,
    Stopping,
    Stopped,
    Faulted
};

enum class SystemHealth : quint8
{
    Healthy = 0,
    Degraded,
    Faulted
};

enum class SystemReadinessFlag : quint32
{
    None = 0,
    DatabaseReady = 1U << 0,
    ConfigurationLoaded = 1U << 1,
    DataDomainReady = 1U << 2,
    ArchiveReady = 1U << 3,
    WebReady = 1U << 4,
    ControlPlaneReady = 1U << 5
};

enum class SystemDegradationFlag : quint32
{
    None = 0,
    ArchiveUnavailable = 1U << 0,
    ArchiveGapDetected = 1U << 1,
    EventGapDetected = 1U << 2,
    StorageSpaceLow = 1U << 3,
    WebUnavailable = 1U << 4,
    ResourcePressure = 1U << 5
};

struct SystemState
{
    qint64 processStartedUtcMs;
    quint32 readinessFlags;
    quint32 degradationFlags;
    ApplicationPhase phase = ApplicationPhase::Starting;
    SystemHealth health = SystemHealth::Healthy;
};
```

`processStartedUtcMs` 在当前 application run 的所有 revision 中保持不变；当前快照生成时间仍由 SampleMeta 表达。
第一版不保存进程 ID、版本字符串、数据库路径或累计指标。

### 5.2 唯一 Owner

`SystemStateOwner` 是轻量低频聚合器，只接收组合根、归档、Web 和控制平面明确报告的就绪/降级变化，再计算
完整 SystemState。它不接收或派发业务 Command，不枚举 Consumer，不读取 TrackPacket，不拥有数据库、线程池
或服务生命周期，也不主动高频轮询组件。

新增状态位必须对应已存在、可检测且可解除的真实状态。详细错误仍发布 SystemEvent；例如归档 gap 可以同时
形成 `ArchiveGapDetected` 当前降级位和一条带缺口参数的 SystemEvent。

## 6. Command、State 与 Event 的一致性顺序

```text
UI 启动命令
  -> DeviceController：DeviceState = Starting，activeRequestId 有效
  -> Per-Device FIFO / ProtocolAdapter / Device
  -> ACK 成功
  -> TaskService：创建 collection_session，得到 AcquisitionId
  -> DeviceController：DeviceState = Collecting，写入 AcquisitionId，清除 activeRequestId
  -> TaskService：TaskState = Running
  -> SystemEvent：记录值得审计的启动成功事实
  -> CommandResult：返回原请求者
```

ACK 超时时，DeviceController 清除 activeRequestId，并根据恢复策略回到 Idle 或进入 Faulted；TaskService 不得
创建虚假采集会话。CommandResult 返回 Timeout，需要观察时另发 Control 域 SystemEvent。

## 7. WebReader 合同

Web 状态服务为三个 State 分别维护 last-seen revision；任意 Doorbell 到达后调用对应 `latest()`，并把完整状态
序列化为 Web snapshot。它不建立统一 `StatusPacket`，也不要求三个 revision 同步递增。

浏览器初次连接必须主动读取三个 State；不能等待下一次 Doorbell。尚未 set 的 State 明确序列化为“未初始化”，
不得伪造默认 Ready、空设备或空闲任务。

## 8. 第一阶段验收标准

1. CoreDataDomain 只新增三个强类型 LatestState，不增加通用状态 Envelope 或中央状态路由。
2. DeviceState 能同时保存多台设备；一次变化后，新 Reader 仅调用一次 latest() 即可恢复全部设备。
3. DeviceState w
4. TaskState 只保存单一活动任务与阶段，不重复 DeviceState 的设备/采集列表。
5. 三个 State 的唯一写入者分别是 DeviceController、TaskService 和 SystemStateOwner。
6. revision、Doorbell 合并、旧只读句柄生命周期和跨线程读写沿用 LatestState 自动化测试。
7. CommandResult、State 和 SystemEvent 通过转换测试证明互不替代。
8. WebReader 能在初次连接和错过 Doorbell 后通过 latest() 恢复完整状态。

## 9. 明确不在本阶段实现

- keyed State registry、DDS QoS 或跨进程共享内存；
- 多个任务同时运行；
- State 历史查询或 revision 持久化；
- 每设备 State Topic、每设备 Doorbell 或每 Consumer State Queue；
- 为尚不存在的设备能力提前扩展状态字段；
- 完整 Command 控制平面和厂家协议字段。

独立按接收steady纳秒计时，2秒进入黄色迟到，5秒进入灰色并清除对应位图；
收到online=0立即黄色，持续收到离线报告则保持黄色。初始灰色，重新收到online=1恢复绿色。
2秒是当前漏包容差，5秒是业务超时。100ms定时检查仅属于Producer状态机，非Consumer轮询。
