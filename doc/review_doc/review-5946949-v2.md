## 结论

航迹显示**功能已闭环**（显示、交互、缩放实时），但 **Core 内航迹主路径有两处绕开架构**，与 `05-核心流程.md` 规定的「经总线、经 Web 接入层」不一致：

| 架构规定 | 当前代码 |
|---------|---------|
| `Processor → Bus publish TrackPoint → TrackDisplayManager subscribe` | `trackPointReady` Qt 信号 **直连** `addPoint` |
| `TrackDisplayManager → WebApiController → WebSocket` | `snapshotReady` 在 **AppController 内联** `ws->broadcast` |

这是当前唯一需要优先修的 **P0 架构债**。其余多为代码质量、前后端契约一致性问题（P1），以及旧文档待同步（P2，改文档不改代码）。

## 问题 1 [P0]：`TrackPoint` 未走 SystemBus，业务层被 Qt 信号直连

**架构依据：**
- `doc/architecture/05-核心流程.md:21-22` — `Adapter → Bus publish TrackPoint → Track dispatch`
- `doc/architecture/02-应用架构.md:23-24, 159-160` — `Access → … → SystemBus → Domain`
- `doc/architecture/03-数据架构.md:29-30` — `TrackRaw → TrackPoint → TrackView`

**当前实现：**
- `RadarDataProcessor.cpp:129-140` — `GeneralPackage` 仍 publish 到总线（`UI_OUTPUTWIDGET`）
- `RadarDataProcessor.cpp:142-160` — `TrackPoint` 通过 **`emit trackPointReady(pt)`** 输出
- `AppController.cpp:399-400` — **`connect(trackPointReady → addPoint)`** 直连 `TrackDisplayManager`

**对比（合规参考）：**
- 工作状态：`BusWorkModeSender` publish → `BusToCommRouter` subscribe（`BusWorkModeSender.cpp`）
- 运行时参数：`WebApiController` publish → `AppController` subscribe → `DphPublisher`（`AppController.cpp:664-671`）

**影响：**
- 违反「发布/订阅不可变」原则；新增订阅者（日志、存储、Task 过滤）无法挂接，只能再拉一条信号线。
- `GeneralPackage` 已上总线但 **`UI_OUTPUTWIDGET` 无订阅者**（全库无 `subscribeByTarget(UI_OUTPUTWIDGET)`），与 `TrackPoint` 信号直连形成 **双通路 + 一端空转**，增加维护困惑。

**建议（不动总线实现，只改业务接线）：**
1. 在 `GenericPackets.h` 增加 `PAYLOAD_TYPE_TRACK_POINT`（及 `pack/unpack TrackPoint`）
2. `RadarDataProcessor` 在映射 `deviceId` 后 **publish TrackPoint** 到总线（`SOURCE_DATA_PROCESSOR`，target 可沿用 `UI_OUTPUTWIDGET` 或新增 `DISPATCH_TRACK_DISPLAY`）
3. `TrackDisplayManager`（或 AppController 薄 bridge + `QMetaObject::invokeMethod` 回主线程）**subscribe** 后调用 `addPoint`
4. 删除 `trackPointReady` 信号直连；评估是否保留 `GeneralPackage → UI_OUTPUTWIDGET` publish（若无订阅者应移除，避免空转）

## 问题 2 [P0]：`TrackDisplaySnapshot` WebSocket 推送绕过 Web 接入层

**架构依据：**
- `doc/architecture/02-应用架构.md:24-26` — `Domain → Api → Web`
- `doc/architecture/05-核心流程.md:24-25` — `Track → API → UI WebSocket`

**当前实现：**
- `AppController.cpp:680-718` — `snapshotReady` 直接连 `WebService::broadcast`，JSON 序列化写在 lambda 内
- `WebApiController.cpp:330-370` — `connectWebPush()` 只处理 Logger 日志与 1s status，**不含 tracks**

**影响：**
- Web 接入层职责被组合根侵占；DTO 转换分散，后续第三方接入需改 `AppController` 而非 `WebApiController`。
- 与「表现层 adapter 输出稳定 DTO」原则不符（`02-应用架构.md:116-120`）。

**建议：**
- 将 snapshot → JSON → `ws->broadcast` **迁入 `WebApiController::connectWebPush()`**（或独立 `TrackSnapshotPushAdapter` 由 WebApiController 持有）
- `AppController` 仅负责装配依赖，不写推送逻辑

## 问题 3 [P1]：`TrackDisplayManager` 输出 style，前端 `TrackLayer` 未消费

**架构依据：**
- `doc/architecture/03-数据架构.md:52, 135` — `TrackDisplaySnapshot` 拥有 display 字段；Web 只依赖 snapshot

**当前实现：**
- 后端 `applyStyle()` 已计算 color/size/opacity（`TrackDisplayManager.cpp:66-87`）
- `TrackLayer.tsx` 保存 `style` 但 `drawTrack()` 使用本地 `TRACK_COLOR` / `SELECTED_COLOR` / `pointIndex < 3` 规则，**不读 `pt.style`**

**判断：** 不违反总线架构，但违反 **数据所有权**（显示样式应来自 snapshot）。前后端各算一套，后续 Qt/Web 双端必分叉。

**建议：** 地图层颜色/点大小优先用 `pt.style`；canvas 特效（尾迹渐变、箭头）可留前端；gray/green 分档逻辑与后端统一（见问题 4）。

## 问题 4 [P1]：`pointIndex` 绝对序号被当作 trail 内相对位置

**位置：**
- `TrackDisplayManager.cpp:78-86` — `pointIndex < 3` 决定 style
- `TrackLayer.tsx:145-146` — 同样按绝对 `pointIndex < 3` 分 gray/green

**问题：** `pointIndex` 是 `(deviceId, trackId)` 生命周期内绝对递增（`03-数据架构.md` 语义）。第 4 个点起整条 trail 不再走「头部强调」分支，与 UI 预期（trail 前段灰色）不一致。

**建议：** 分档改用 **缓存/trail 内相对下标**（如 `i >= len - GRAY_HEAD_COUNT`）；前后端同一算法。旧 `doc/business/航迹显示数据管理.md` 中的样式描述若与此冲突，**以代码修正后的行为更新 business 文档**。
