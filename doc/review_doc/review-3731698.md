# Review 3731698

## 结论

这一版开始实现“任务切换加载上下文”的最小 UI，整体方向是对的：

1. `CoreProvider` 接收 `activeTaskId`。
2. 前端状态已分成 `tracks` 和 `historyTracks`。
3. active task 切换时会加载历史航迹和系统事件。
4. 新增 `HistoryTrackLayer`，历史层和实时层视觉上分开。
5. `BottomPanel` 开始展示当前任务事件和历史加载状态。

但有一个必须继续处理的架构问题：**实时 WS 航迹流还没有按 active task 过滤或携带 taskId，前端切换任务时清空实时层后，下一帧 WS snapshot 仍可能把实时层重新填满。**

这会削弱“任务切换清空实时显示”的语义。

## 本轮做对的点

### 1. 实时层和历史层没有混用

位置：

- `ui/src/hooks/useCoreApi.tsx`

新增状态：

```ts
tracks          // 实时层
historyTracks   // 历史层
systemEvents    // 当前任务事件
```

这是正确方向。  
历史航迹没有被转换成 `RadarTrack` 后塞进实时 `tracks`。

### 2. 任务切换时加载历史上下文

位置：

- `ui/src/hooks/useCoreApi.tsx`

active task 变化时会：

1. `clearLiveTracks()`
2. 无 active task 时清空历史状态
3. 有 active task 时并行加载：
   - `fetchTrackHistory({ taskId, limit: 1000, order: 'asc' })`
   - `fetchSystemEvents({ taskId, limit: 200 })`

并且有 `cancelled` 标记，能避免旧请求完成后回写新任务状态。

这点做得对。

### 3. 历史航迹层视觉上和实时层分开

位置：

- `ui/src/components/map/HistoryTrackLayer.tsx`
- `ui/src/components/map/MapRadarView.tsx`

历史层：

- 淡色
- `z-[15]`

实时层：

- 仍由 `TrackLayer` 绘制
- `z-20`

视觉层级符合预期：实时更突出，历史更弱。

### 4. 底部面板开始展示任务事件

位置：

- `ui/src/components/panels/BottomPanel.tsx`

当前展示：

- 历史加载状态
- 历史加载错误
- 当前任务事件列表

这是一个合理的最小 UI。

## 必须继续处理的问题

### P1. 实时 WS tracks 仍可能跨任务污染当前显示

位置：

- `ui/src/hooks/useCoreApi.tsx`
- `msg.type === 'tracks'` 分支
- `core/web/TrackDisplayWebBridge.cpp`
- `TrackPoint.taskId`

现状：

active task 切换时，前端会执行：

```ts
clearLiveTracks()
```

这会清空：

- `tracksRef`
- `tracks`
- `trackRate`
- pending interaction

但 WebSocket 仍在持续推送实时 snapshot。只要下一帧：

```ts
msg.type === 'tracks'
```

前端就会把 `msg.tracks` 直接写入：

```ts
tracksRef.current = msg.tracks.map(...)
flushTracksToState()
```

也就是说，如果后端 WS snapshot 没有按当前 active task 过滤，或者没有带 `taskId` 让前端过滤，那么“切换任务清空实时显示”只能维持到下一帧 WS 消息。

这会造成用户看到：

```text
切到任务 B
实时层短暂清空
随后又出现任务 A 或未归属任务的实时航迹
```

这不符合任务上下文语义。

建议 Cursor 下一步优先处理：

方案 A，推荐：

```text
后端 TrackDisplay snapshot 只发布当前 active task 可见的实时航迹
```

也就是 core 在 TrackDisplayManager / WebBridge 之前就按 task context 过滤。

方案 B，过渡方案：

```text
WS tracks payload 携带 taskId，前端按 activeTaskId 过滤
```

但这会让前端承担一部分业务过滤，不如方案 A 干净。

最少也要先让 WS tracks 的每个点带上 `taskId`，因为 `TrackPoint` 里已经有该字段。

### P2. `HistoryTrackLayer` 没有按时间断点分段，可能把不连续航迹连成线

位置：

- `ui/src/components/map/HistoryTrackLayer.tsx`

当前按：

```ts
targetId -> sort(tsMs) -> 一条 polyline
```

如果同一个 `targetId` 在历史中出现间隔很大的点，或者任务内存在数据中断，当前会直接连线。

短期可以接受。  
但后续建议加一个简单断点规则，例如：

```text
相邻点时间差 > N 秒，则断开 polyline
```

这不是当前阻断点，但会影响历史轨迹观感。

### P2. 历史航迹按勾选设备显示，这个语义需要确认

位置：

- `ui/src/components/map/MapRadarView.tsx`

当前历史层只渲染：

```ts
devices.filter(d => checkedDeviceIds.includes(d.id))
```

也就是说，如果任务绑定了某个设备，但用户没有勾选该设备，历史轨迹不会显示。

这可能是合理的，因为勾选设备本来就控制地图显示。  
但需要确认产品语义：

- 勾选设备控制实时和历史两层？
- 还是历史层默认显示当前任务所有设备？

建议暂时保留当前实现，但文档里明确：设备勾选同时控制实时层和历史层。

### P3. systemEvents 展示 key 用 index，后续可换稳定 key

位置：

- `ui/src/components/panels/BottomPanel.tsx`

当前：

```tsx
systemEvents.slice(0, 20).map((ev, i) => <div key={i}>)
```

第一版可以接受。  
后续如果事件列表会刷新、插入、筛选，建议用：

```text
tsMs + category + source
```

作为更稳定的 key。

## 架构判断

这一版前端分层方向正确，但实时层的 source of truth 还没有完全进入任务上下文。

当前已经完成：

```text
历史层：taskId -> fetchTrackHistory -> historyTracks -> HistoryTrackLayer
事件层：taskId -> fetchSystemEvents -> systemEvents -> BottomPanel
```

仍需补齐：

```text
实时层：activeTaskId -> WS tracks 可见性
```

否则任务切换时，历史层是任务上下文的，但实时层仍可能是全局上下文的。

## 代码质量评估

当前 UI 代码质量整体可以接受，属于正确的第一版：

- 状态拆分清楚
- 异步加载有取消保护
- 历史层和实时层未混用
- UI 没有过度复杂化

主要风险集中在实时 WS snapshot 没有 task-aware。

## 建议 Cursor 下一步

优先级：

1. 让实时 WS tracks 具备任务上下文：
   - 推荐后端按 active task 过滤 TrackDisplay snapshot
   - 至少先让 WS tracks payload 携带 `taskId`
2. 前端在接收 tracks snapshot 时，不应显示不属于当前 active task 的实时航迹。
3. 明确设备勾选是否同时控制实时层和历史层。
4. 后续再优化 HistoryTrackLayer 的断点分段。

当前不要继续加复杂 UI。先把“实时层也服从任务上下文”补齐。
