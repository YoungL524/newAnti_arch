## 推荐下一步：Milestone 2 - RuntimeSettings / DPH 参数链路

优先级我建议放在 RuntimeSettings，而不是先做 TrackDisplayManager。

原因：

1. 现在设备台账已经能回答“控制哪台设备”。
2. 下一步必须回答“以什么运行参数控制设备”。
3. DPH 参数和 UI 强相关，如果不先定边界，后面会继续出现 UI 字段直接牵动协议结构体的问题。
4. RuntimeSettings 做好后，任务状态机和航迹显示都能引用稳定的运行上下文。

### 建议先让 Claude 写文档，不直接写代码

新增：

```text
doc/business/运行时参数管理.md
```

文档先明确：

- `DPH` 是外部协议结构体，不是 UI model。
- `RuntimeSettings` / `RadarRuntimeConfig` 是内部业务运行参数模型。
- UI 修改参数后通过 API 写入后端运行参数服务。
- 后端运行参数服务发布 `DphParamsChanged` 事件。
- `DphPublisher` 订阅事件，缓存最新参数。
- 50ms 定时发送时只使用本地缓存，不主动向 UI 或 API 拉取。
- 前端不改参数就不发事件；后端继续使用上一次有效参数。

推荐链路：

```text
UI 参数编辑
  -> WebApiController
  -> RuntimeSettingsService
  -> DphParamsChanged event
  -> DphPublisher 更新本地缓存
  -> QTimer 每 50ms 使用缓存组 DPH 并发送
```

### 最小代码切入点

文档确认后，再让 Claude 做最小实现：

1. 新增 `RuntimeSettingsService`，只先管理 DPH 必需字段。
2. 新增内部 DTO，避免 UI 直接依赖协议结构体字段名。
3. `DphPublisher` 增加 `applyRuntimeSettings(...)` 或订阅 bus event。
4. API 先做最小：
   - `GET /api/runtime-settings`
   - `PUT /api/runtime-settings`
5. 不急着落库，先保证运行时链路清晰。

## Milestone 3 先做接口文档，不急着实现

Track 这条线你已经修正过方向：上位机不负责航迹起批、消失、融合等算法；我们做的是航迹显示数据管理。

建议先新增：

```text
doc/api-core-web-track-protocol.md
doc/business/航迹显示数据管理.md
```

先把固定协议定下来：

- `trackId`
- `deviceId`
- `timestamp`
- 坐标 / 距离 / 方位 / 高度
- 点序号或显示阶段
- 当前样式：颜色、尺寸、透明度、是否高亮、是否追踪使能
- 用户操作状态：selected / trackingEnabled
- 数据转发目标或转发状态

等 RuntimeSettings 的边界立住后，再实现 `TrackDisplayManager` 会更稳。
