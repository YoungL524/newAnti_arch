## Findings

### P1 - 前端仍未把勾选设备传给 `/api/start` / `/api/stop`

- File: `ui/src/hooks/useCoreApi.tsx`
- Lines: 76-94
- File: `core/web/WebApiController.cpp`
- Lines: 96-148

后端这版新增了 `acceptedDeviceIds` / `rejectedDeviceIds`，并且在 `deviceIds` 非空但没有可控设备时返回失败，这是对上一轮假成功问题的正确方向。

但前端实际调用仍然是：

```ts
fetch(`/api/${isWorking ? 'stop' : 'start'}`, { method: 'POST' })
```

也就是说 `checkedDeviceIds` 只用于“未勾选时禁止启动”的 UI 判断，没有进入请求 body。结果是：

- 用户勾选任何业务设备后点击开始；
- 前端请求 body 为空；
- 后端按空数组逻辑默认接受 `radar_cpu`；
- 用户以为控制的是勾选设备，实际控制的是 legacy `radar_cpu`。

这会让 Milestone 1 的设备台账 source of truth 失去意义。现在后端已经准备接收 `deviceIds`，前端必须把 `checkedRef.current` 传过去，并消费后端返回结果。

建议 Claude Code 修改：

1. `toggleAcquisition` 请求体增加：

```ts
body: JSON.stringify({ deviceIds: cids })
headers: { 'Content-Type': 'application/json' }
```

2. 解析响应中的 `ok`、`acceptedDeviceIds`、`rejectedDeviceIds`。
3. 如果 `ok:false` 或 `acceptedDeviceIds` 为空，撤销本地 optimistic `acquisition` 状态，并给用户可见错误。
4. 如果存在 `rejectedDeviceIds`，至少记录到 UI 日志/状态栏，不能只在 console 里消失。

### P1 - 启停失败后前端仍乐观切换采集状态且不回滚

- File: `ui/src/hooks/useCoreApi.tsx`
- Lines: 72-96

`toggleAcquisition` 会先本地切换 `acquisition`，然后 fire-and-forget 调接口：

```ts
setState(prev => ({ ...prev, acquisition: !isWorking, ... }))
fetch(...).catch(() => {})
```

后端这版已经可能返回 `{ ok:false }`，但前端没有读取响应。网络失败、后端拒绝、设备不支持、节流返回等情况都会让 UI 状态短时间甚至长期与后端真实状态不一致。

建议 Claude Code 修改：

1. 把 `toggleAcquisition` 改成 async command。
2. 可以保留 pending 状态，但不要在后端确认前长期相信 optimistic state。
3. 成功后等待下一次 status/WS 校正，或直接按 accepted result 更新 command 状态。
4. 失败时恢复 `acquisition/isWorking`，并显示错误。

### P1 - `pendingRef` 在“未勾选设备”分支提前置位，导致用户 1.5 秒内无法再次操作

- File: `ui/src/hooks/useCoreApi.tsx`
- Lines: 72-82

当前逻辑先设置：

```ts
pendingRef.current = true
setTimeout(() => { pendingRef.current = false }, 1500)
```

然后才判断：

```ts
if (!isWorking && cids.length === 0) {
  setState(prev => ({ ...prev, noSelectionHint: true }))
  return
}
```

所以用户第一次没勾选设备点击开始后，即使马上勾选设备，也要等 1.5 秒才能再次点击生效。这是一个很小但很扎手的交互 bug。

建议 Claude Code 修改：

1. 先做未勾选校验，再进入 pending/throttle。
2. 或者在该分支 return 前恢复 `pendingRef.current = false`。

### P2 - 状态去重采用“跳过 registry 设备”，会丢失设备台账元数据

- File: `core/web/WebApiController.cpp`
- Lines: 40-66
- File: `core/web/WebApiController.cpp`
- Lines: 311-333

上一轮指出重复 id 会破坏前端状态。这版用 `QSet<QString> emittedIds` 避免重复，方向没错。

但当前策略是先输出 legacy `radar_cpu`，如果 registry 里也有 `radar_cpu`，就直接跳过 registry 设备。这样会导致状态接口丢掉设备台账中的：

- `name`
- `kind`
- 坐标
- 厂家/型号
- endpoint 绑定
- 阵面/配置类字段

从架构上看，设备台账应该是 source of truth，运行状态应该 merge 到台账设备上，而不是 legacy 状态覆盖台账对象。

建议 Claude Code 修改：

1. 先遍历 `DeviceRegistry` 输出业务设备对象。
2. 如果某个设备映射到 legacy controller，再把 `state/acquisition` merge 到该设备。
3. 只有 registry 中完全没有对应设备时，才输出 fallback `radar_cpu`。
4. REST status 和 WS status 的 merge 逻辑抽成一个 helper，避免两处复制后继续漂移。

### P2 - 后端节流响应仍返回 `ok:true`，但没有 accepted/rejected 明细

- File: `core/web/WebApiController.cpp`
- Lines: 112-114
- File: `core/web/WebApiController.cpp`
- Lines: 133-135

当 500ms 内重复点击时，接口返回：

```json
{ "ok": true, "throttled": true }
```

但这次没有执行控制命令，也没有 `acceptedDeviceIds/rejectedDeviceIds`。如果前端开始消费 accepted/rejected，这个响应会成为特殊分支；如果继续只看 `ok:true`，UI 会以为命令已经执行。

建议 Claude Code 修改：

1. 节流响应不要使用普通成功语义，可以返回 `ok:false, throttled:true`。
2. 或返回 `ok:true, throttled:true, acceptedDeviceIds: []` 并让前端明确识别“未执行新命令”。
3. 前后端契约文档要写清楚 throttled 是否代表命令被接受。
