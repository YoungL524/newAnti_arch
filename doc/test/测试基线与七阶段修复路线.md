# 测试基线与七阶段修复路线

> 目的：建立可重复、可定位、分层隔离的测试体系，并按照架构目标逐步收敛当前实现。
>
> 使用方式：每个阶段必须先满足“进入条件”，完成该阶段的自动化测试和人工验收后，再进入下一阶段。修复过程中保持程序可构建、可启动、可回退。

## 当前基线状态（2026-07-20）

- 独立构建目录：`build-test`
- CMake：配置成功，`BUILD_TESTS=ON`
- C++/Qt：编译成功
- CTest：7/7 通过
- React/Vite：生产构建成功
- 统一入口：`pwsh -File scripts/test_baseline.ps1`
- 当前阶段：阶段一完成，下一步进入阶段二“收敛航迹类型模型”

本次基线还修正了 `RadarWorkModeController` 测试夹具的状态推进错误：从 `Working` 构造 `Fault` 时必须模拟停止命令失败，不能重复发送工作命令。

## 1. 总体原则

### 1.1 每层都要有独立测试手段

| 层级 | 主要测试方式 | 关注点 |
| --- | --- | --- |
| 协议/算法纯函数 | Qt Test 单元测试 | 字段布局、字节序、单位、边界值、异常输入 |
| 数据模型与配置 | Qt Test + 临时 SQLite/临时目录 | 校验、序列化、迁移、事务和约束 |
| 业务服务 | Qt Test + fake sender/repository | 状态机、生命周期、权限和业务不变量 |
| SystemBus | Qt Test | 发布、订阅、顺序、队列上限、丢弃计数 |
| 通信接入 | 本地 UDP/TCP loopback | 收发、端点路由、超时、重连和错误 |
| Web API | HTTP 集成测试 | 状态码、DTO、鉴权边界、错误响应 |
| WebSocket | WebSocket 集成测试 | 快照、状态、断线重连、消息版本 |
| React 组件/hooks | Vitest + React Testing Library | 渲染、交互、状态转换、异常态 |
| 前后端链路 | test_comm + core + 浏览器/脚本 | 真实协议闭环和时延 |
| 部署产物 | 干净目录启动测试 | DLL、配置、数据库路径和端口 |

### 1.2 测试分层

```text
L0 编译检查
  ↓
L1 纯单元测试（不启动网络、不依赖真实数据库）
  ↓
L2 模块测试（临时 SQLite、fake 通信、fake 总线）
  ↓
L3 Core 集成测试（真实 Web/UDP/SQLite）
  ↓
L4 全链路验收（core + test_comm + React）
```

任何阶段失败时，优先在最低层级复现，不直接用全链路现象猜原因。

### 1.3 固定基线命令

后续应将以下命令收敛为 CI 或本地脚本：

```powershell
# 后端配置（测试必须打开）
cmake -S . -B build-test -G "MinGW Makefiles" `
  -DBUILD_TESTS=ON `
  -DCMAKE_BUILD_TYPE=Debug `
  -DCMAKE_PREFIX_PATH="C:/Qt/Qt5.14.2/5.14.2/mingw73_64"

cmake --build build-test --parallel
ctest --test-dir build-test --output-on-failure

# 前端
cd ui
npm ci
npm run build
```

> 当前 `build` 缓存曾使用 `BUILD_TESTS=OFF`，不能用其中的旧测试可执行文件代表当前源码测试结果。测试基线应使用独立的 `build-test` 目录。

## 2. 阶段一：建立可信构建与测试基线

### 目标

让任何开发者都能在干净构建目录中完成配置、编译、测试，并能区分源码问题、环境问题和权限问题。

### 工作项

- 固定 Qt、MinGW、CMake、Node.js 版本和路径检查；
- 新建独立 `build-test`，启用 `BUILD_TESTS=ON`；
- 确认全部 Qt Test 被 CTest 注册；
- 修复测试目录和生成文件权限问题；
- 为前端加入 TypeScript、Vite、ESLint 检查；
- 增加统一 `scripts/test_all.ps1` 或等价入口；
- 记录 Debug/Release 两套构建结果，不混用性能数据；
- 确认 `build/bin` 脱离源码目录仍可启动。

### 必须覆盖的现有测试

- `ConfigManager`
- `HttpParser`
- `PipelineLatencyMonitor`
- `TrackPacketMapper`
- `ProtocolLayout`
- `RadarWorkModeController`
- `TaskService`

### 验收标准

- `cmake --build build-test` 成功；
- `ctest --test-dir build-test --output-on-failure` 全部通过；
- 前端 `npm run build` 成功；
- 测试失败时能显示具体测试名和日志；
- 不依赖开发机已有的 `build`、`data` 或旧数据库。

### 产出物

- 可重复的构建/测试脚本；
- 测试目录说明；
- 第一份基线测试报告；
- 初始覆盖率或至少测试模块清单。

## 3. 阶段二：收敛轻量航迹包

### 目标

固定从厂家协议到业务航迹的类型边界，禁止厂家结构体和固定裸缓冲进入业务总线。

### 工作项

- 定义唯一的轻量 `TrackPacket`；
- `GeneralPackage` 只在输入协议适配器内部临时存在；
- `TrackPacket` 覆盖来源、归属、运动学和识别状态；
- 识别前后使用同一对象，通过 `recognitionStatus` 区分处理阶段；
- 定义 `TrackDisplayUpdate`（snapshot/delta）；
- 统一角度、距离、速度、时间戳和坐标单位；
- 为 `TrackPacket` 增加 schemaVersion、traceId、taskId、deviceId；
- 为每种消息建立序列化/反序列化测试；
- 保留旧消息路径作为短期兼容层，并明确删除计划。

### 单元测试

- 默认值和必填字段；
- 单位转换和边界值；
- 空批次、超大批次和重复 trackId；
- 消息版本不兼容；
- task/device 上下文缺失；
- 发布前使用移动语义，发布后通过 `shared_ptr<const TrackPacket>` 只读共享；
- 多订阅者不深拷贝整条航迹，也不能修改权威数据。

### 验收标准

- `GeneralPackage` 不出输入适配边界；
- 航迹主干不再使用固定 `rawData[4096]`；
- 只有识别完成的 `TrackPacket` 可以进入 SystemBus；
- UI DTO 不包含厂家字段；
- 同一批航迹只构造一次标准 payload；
- 日志能用 messageId/correlationId 关联关键节点。

## 4. 阶段三：打通识别主干

### 目标

即使尚无真实算法，所有正式业务航迹也必须经过识别模块。

### 工作项

- 定义 `IRecognitionModule`；
- 实现 `PassThroughRecognitionModule`；
- 输入并处理同一个 `TrackPacket`；
- 识别结果默认 `Unknown`，状态从 Pending 变为 Completed；
- 只在识别完成后发布一次 SystemBus；
- 增加识别排队、处理和发布时延统计；
- 模拟识别失败、超时和空结果。

### 测试

- 透传字段完整性；
- Unknown 结果和版本字段；
- 空输入、异常输入和模块拒绝；
- 消息顺序和 task/device 归属；
- 识别模块不直接访问 Web、数据库和厂家协议。

### 验收标准

```text
InputAdapter → TrackPacket(Pending)
→ PassThroughRecognition → TrackPacket(Completed) → SystemBus
```

显示、存储和未来消费者都只能订阅识别完成的只读 `TrackPacket`。

## 5. 阶段四：迁移显示与存储

### 目标

消除 `RadarDataProcessor::trackPointReady` 到显示模块的直连，使显示和持久化成为识别后航迹的独立消费者。

### 工作项

- `TrackDisplayManager` 改为订阅 `shared_ptr<const TrackPacket>`；
- 删除或隔离 `trackPointReady` 直连路径；
- `TrackDisplayUpdate` 通过 SystemBus 到 `TrackDisplayWebBridge`；
- 航迹存储改为独立旁路消费者；
- 引入有界存储队列、批量事务和失败重试/告警；
- 日志和性能指标不得阻塞显示主链路；
- 保留旧路径的对照开关，便于同负载时延对比。

### 测试

- 同一识别批次同时被显示和存储消费；
- 显示消费者变慢时不阻塞识别；
- 数据库不可用时显示仍可用；
- 队列满时计数、告警并按策略丢弃；
- task 切换时显示缓存正确清理；
- 延迟 interaction 命令不会修改下一任务的航迹。

### 验收标准

- Processor 不直接调用 DisplayManager 或 DataStore；
- 断开 SQLite 后 Web 实时显示仍能继续；
- `doc/test/时延链路-验证清单.md` 中的阶段指标仍满足基线；
- P95/P99 没有不可接受退化。

## 6. 阶段五：实现第三方转发纵向切片

### 目标

先实现一个可测试的模拟输出协议，验证第二条主业务链路，而不是一开始同时开发多个厂家协议。

### 工作项

- 定义 `IForwardingModule`；
- 定义 `IOutputProtocolAdapter`；
- 实现一个 Demo/JSON/固定二进制输出适配器；
- 从识别完成的 `TrackPacket` 订阅；
- 通过端点绑定选择目标；
- 交给 `CommunicationManager` UDP 发送；
- 为转发增加独立 trace 和时延阶段；
- 增加不可静默丢弃的转发队列策略。

### 测试

- 识别后航迹才能触发转发；
- 不同设备路由到不同 endpoint/target；
- 编码字段、字节序和版本；
- UDP 发送失败、端点不存在、队列满；
- 显示或数据库故障不影响转发；
- 第三方协议不泄漏到 Web DTO。

### 验收标准

```text
TrackPacket(Completed)
→ ForwardingModule
→ OutputProtocolAdapter
→ CommunicationManager
→ test_comm/模拟接收器
```

至少有一个自动化接收端能验证完整字节帧。

## 7. 阶段六：完善设备级工作状态控制

### 目标

从当前单 `radar_cpu` 控制器升级为每台雷达独立状态机和精确命令路由。

### 工作项

- 引入 `WorkModeControllerRegistry`；
- 每个可控设备创建独立 `RadarWorkModeController`；
- 设备 id、endpoint id、target name 三者严格绑定；
- 多设备 start/stop 明确逐项结果；
- 用真实 ACK/回显替代纯超时乐观确认；
- 一台设备 Fault 不影响其他设备；
- UI 状态按设备聚合而不是共享全局状态。

### 测试

- 两个控制器完全独立；
- 单设备启动、停止、复位；
- 一台设备发送失败；
- ACK 匹配、错误 ACK、超时和重复 ACK；
- 多设备部分成功/部分失败；
- 命令路由不串设备。

### 验收标准

- `/api/status` 能返回每台设备真实状态；
- 多选操作不会只执行第一个设备；
- 设备状态、PPI 扫描状态和 WebSocket 状态一致。

## 9. 阶段门禁与回退规则

每阶段结束时必须记录：

```text
源码版本 / 构建类型 / 测试命令 / 测试结果
输入负载 / 设备数量 / 航迹数量 / 客户端数量
P50 / P95 / P99 / 最大值 / 丢弃数
已知问题 / 回退方式 / 下一阶段入口
```

以下情况不得进入下一阶段：

- 基线测试不全通过；
- 新增模块没有独立测试手段；
- 失败路径没有可观察日志或错误码；
- 主链路 P95/P99 明显退化且没有解释；
- 测试依赖开发机残留数据库、配置或进程；
- 为修复一个模块而绕过既定消息和分层边界。

每次迁移保留一个可编译的过渡版本。新链路稳定后再删除旧链路，不允许先删除旧实现再寻找替代路径。

## 10. 当前执行顺序

当前应从阶段一开始，具体顺序为：

1. 清理/重建 `build-test`，开启 `BUILD_TESTS=ON`；
2. 让 CTest 正确发现并运行全部现有 Qt 测试；
3. 补齐前端构建检查和最小组件测试；
4. 记录第一份测试和时延基线；
5. 再开始阶段二的航迹类型设计。

在阶段一没有完成之前，不建议直接重构 `RadarDataProcessor` 或引入真实识别算法，否则问题会混合在环境、测试和架构改造中，难以定位。
