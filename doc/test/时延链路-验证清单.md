# 时延链路验证清单

## 1. 前置条件

- core 与 test_comm 正常运行；
- 已激活包含当前雷达设备的任务；
- UI 能正常显示航迹；
- 连续发送足够多的航迹样本，建议至少 1000 个。

## 2. 查询方式

```powershell
Invoke-RestMethod http://localhost:8088/api/metrics/latency |
  ConvertTo-Json -Depth 5
```

所有阶段单位均为微秒。`sampleCount` 是启动以来累计样本数，分位数基于最近最多 4096 个样本。

## 3. 基本验收

1. `decode.sampleCount` 随合法雷达包增加；
2. 活动任务航迹可见时，`ingressToDisplay.sampleCount` 随航迹增加；
3. `snapshotBuild`、`snapshotBusDispatch`、`webQueue` 和 `webPrepareAndBroadcast` 大约每秒增加一次；
4. 每个阶段满足 `min <= p50 <= p95 <= p99 <= max`；
5. 停止航迹输入后，逐航迹阶段样本数不再增长；
6. 重启 core 后内存统计重新计数。

等待至少 10 秒后检查 SQLite：

```sql
SELECT window_end_ms, stage, sample_count, p50_us, p95_us, p99_us, max_us
FROM pipeline_metrics
ORDER BY id DESC
LIMIT 30;
```

日志中应出现类似内容：

```text
[Latency] ingressToDisplay count=1000 p50=40us p95=80us p99=120us max=300us
```

日志目录是 `<core可执行文件目录>/data/logs`。CMake 默认构建时通常对应 `build/bin/data/logs`，不是固定的仓库根目录 `data/logs`。

## 4. 对比方法

固定以下条件后再比较改造前后或不同版本：

- 相同电脑和构建类型（Debug/Release 不混比）；
- 相同 test_comm 发包速率；
- 相同活动任务、设备数量和航迹数量；
- 相同 UI 客户端数量；
- 相同数据库和日志配置；
- 先预热 30 秒，再采集至少 5 分钟。

重点比较 `p95Us`、`p99Us` 和 `maxUs`，不要只看平均值。

## 5. 指标边界

- 不包含 1 秒显示快照定时等待；
- 不包含浏览器网络接收和 React 绘制；
- `webPrepareAndBroadcast` 统计到调用 WebSocket broadcast 返回，不等待客户端确认；
- 当前没有第三方航迹转发模块，因此尚无“接收航迹到第三方发送”的正式指标；该指标将在转发模块实现时沿用同一 trace 补充。
