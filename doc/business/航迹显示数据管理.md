# 航迹显示数据管理

## 概述

上位机不负责航迹起批、消失、融合等算法（属于数据处理系统职责）。航迹显示数据管理接收识别主干输出的标准航迹，转为固定 Web 协议并维护显示状态。它不解析厂家协议，也不执行目标识别。

## 架构边界

```
endpointId
  → InputProtocolAdapter 查询 DeviceRegistry / endpoint binding
  → TrackPacket(Pending)
  → RecognitionModule（同一个包标记 Completed）
  → SystemBus（只发布一次）→ TrackDisplayManager
  → TrackDisplayUpdate（初始 snapshot / 稳态 delta）
  → SystemBus → TrackDisplayWebBridge / WS → 前端
```

关键依赖：
- 标准航迹中的 `deviceId` 必须是 `DeviceRegistry` 业务设备 id（如 `radar_001`）
- `endpointId → deviceId` 映射由输入适配阶段完成，`TrackDisplayManager` 不接触 endpoint
- `TrackDisplayManager` 只订阅识别完成的只读 `TrackPacket`，不订阅厂家原始包或未识别航迹
- WS 新连接、任务切换和重同步发送有界 snapshot；稳态每 1s 只发送 upserts/removals delta
- TrackDisplayManager 内部状态索引使用复合 key `(deviceId, trackId)`

## 历史 TrackPoint — 已删除

```cpp
struct TrackPoint {
    QString deviceId;            // DeviceRegistry 业务设备 id（RadarDataProcessor 完成映射）
    uint32_t trackId;            // 航迹号
    qint64 timestampMs;
    double range;
    double azimuth;              // rad
    double elevation;            // rad
    double radialSpeed;
    double rcs;
    double altitude;
    double x, y, z;
    uint32_t sceneNumber;
};
```

- 该结构及 `trackPointReady` Qt signal 已于统一航迹总线接通后删除。
- `deviceId` 在 `RadarDataProcessor` 内通过 `endpointId → DeviceRegistry` 查询完成
- `TrackDisplayManager` 不查询 `DeviceRegistry`，不关心 `endpointId`
- 当前输入是 SystemBus 上的 `DataPacket{DataCommand::Track, shared_ptr<const TrackPacket>}`。

## 显示缓存保留策略

上位机不判断航迹是否在物理上消失。但显示层必须有缓存保留策略：

- 不设置单条 `(deviceId, trackId)` 的固定点数上限
- 所有活动航迹共享 50000 点的显示缓存预算，超出时全局丢弃最旧点，避免某一条航迹独占内存
- 连续 5s 未更新的航迹只从显示缓存移除；这属于 UI 缓存回收，不代表上位机判定航迹消失
- 当前发布窗口最多保留全局最新 600 个点；历史完整数据仍由 DataStore 按任务保存

## WS 消息格式（初始快照 + 增量）

```typescript
interface WsTrackSnapshotMessage {
  type: 'tracks'
  mode: 'snapshot'
  revision: number
  timestamp: number
  tracks: TrackDisplayPoint[]
}

interface WsTrackDeltaMessage {
  type: 'tracks'
  mode: 'delta'
  revision: number
  timestamp: number
  upserts: TrackDisplayPoint[]
  removals: Array<{ deviceId: string; trackId: number; pointIndex: number }>
}

interface TrackDisplayPoint {
  trackId: number
  deviceId: string              // DeviceRegistry 业务设备 id
  taskId: string                // 当前活动任务 id
  timestamp: number

  range: number
  azimuth: number
  elevation: number
  radialSpeed: number
  altitude: number

  // 显示状态
  pointIndex: number            // 该 (deviceId, trackId) 自接收以来绝对递增序号
                                // 不是缓存数组下标，FIFO 裁剪后不会重置
  style: {
    color: string
    size: number
    opacity: number
  }
  interaction: {
    selected: boolean
    trackingEnabled: boolean
  }
}
```

实时 Web DTO 为降低帧大小不下发内部 `x/y/z/rcs`；如后续 Web 业务需要，必须通过固定协议版本显式扩展。

## TrackDisplayManager 内部状态

```cpp
struct TrackKey {
    QString deviceId;
    uint32_t trackId;
};
```

- 内部 interaction map 及缓存均以 `TrackKey` 为索引
- 不用裸 `trackId`，避免多设备同航迹号冲突

## TrackDisplayManager 职责

- 接收识别完成的 `TrackPacket`（已含业务 `deviceId` 和识别结果）
- 按 `TrackKey` 维护点序列和绝对递增 `pointIndex`
- 根据全局 50000 点缓存预算、5s 无更新回收和 600 点发布窗口管理显示资源
- 管理 `interaction` 状态
- 根据 `pointIndex` 和用户交互状态生成 `style`
- 每 1s 对当前 600 点窗口与上次已发布状态做 diff，输出 `TrackDisplayUpdate`
- 新连接由 `TrackDisplayWebBridge` 单独发送其维护的权威 snapshot

非职责：
- 不查询 `DeviceRegistry`
- 不关心 `endpointId`
- 不判断航迹起批、消失、融合
- 不做目标识别

## Interaction 状态更新

interaction 状态在 `TrackDisplayManager` 内部通过复合 key 维护。

```http
PUT /api/devices/{deviceId}/tracks/{trackId}/interaction
Content-Type: application/json

{
  "selected": true,
  "trackingEnabled": false
}
```

响应：

```json
{
  "ok": true,
  "interaction": {
    "taskId": "task_...",
    "deviceId": "radar_001",
    "trackId": 1,
    "selected": true,
    "trackingEnabled": false
  }
}
```

- `WebApiController` 仅接受当前活动任务内设备的命令，并将当前 `taskId` 写入 `TrackInteractionCommand`
- `TrackDisplayManager` 仅更新当前任务中仍存在的 `(deviceId, trackId)`，延迟到下一任务的命令会被拒绝
- interaction 更新会立即生成对应点的 upsert delta
- `selected` 与 `trackingEnabled` 独立存储

## endpointId 映射约束

`endpointId → deviceId` 映射必须唯一：

```
对于会产生航迹数据的采集 endpoint，同一时刻只能绑定一个 Radar 业务设备。
```

- `DeviceRegistry::findRadarByEndpointId(endpointId)` 提供按端点查询接口（只匹配 Radar 设备）
- 非空 `endpointId` 在 `create`/`update` 时做应用层冲突检查（同 kind=Radar 不重复）
- 活动任务正在使用的设备不得被解除端点，也不得被其他设备迁走端点
- 如果 `RadarDataProcessor` 收到数据但 `endpointId` 未绑定 Radar 业务设备：标准 `TrackPacket` 会因缺少业务设备归属而被显示管理器拒绝
- 如果 `endpointId` 绑定多个 Radar 业务设备：记录 `qWarning`，返回空映射，标准航迹不会进入可见显示状态（宁可不显示，不挂错设备）

## 与现有模块的关系

- `InputProtocolAdapter`：厂家协议 → `TrackPacket(Pending)`，填入业务 `deviceId`
- `RecognitionModule`：处理同一个 `TrackPacket` 并标记 Completed/Unknown；当前待实现透传识别器
- `TrackDisplayManager`：订阅识别后航迹，输出 `TrackDisplayUpdate`
- `TrackDisplayWebBridge`：订阅显示更新、维护连接快照并转换为固定 WebSocket DTO

`RadarDataProcessor::trackPointReady -> TrackDisplayManager::addPoint` 直连路径已经删除；显示只消费统一 `DataPacket{Track}`。

### 前端同步规则

- snapshot 原子替换本地窗口，delta 必须按 `revision` 连续应用；
- revision 缺口或本地消息积压超过上限时主动断开重连，由新连接 snapshot 恢复；
- 删除键精确到 `(deviceId, trackId, pointIndex)`，滚动窗口不会在浏览器无限增长；
- `TrackLayer` 仍只负责渲染合并后的权威点集。
