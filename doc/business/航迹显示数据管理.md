# 航迹显示数据管理

## 概述

上位机不负责航迹起批、消失、融合等算法（属于数据处理系统职责）。航迹显示数据管理接收识别主干输出的标准航迹，转为固定 Web 协议并维护显示状态。它不解析厂家协议，也不执行目标识别。

## 架构边界

```
endpointId
  → InputProtocolAdapter 查询 DeviceRegistry / endpoint binding
  → NormalizedTrackBatch（业务 deviceId，不携带通信 endpointId）
  → SystemBus → RecognitionModule
  → IdentifiedTrackBatch
  → SystemBus → TrackDisplayManager
  → TrackDisplaySnapshot（固定 Web 协议，全量 snapshot）
  → SystemBus → TrackDisplayWebBridge / WS → 前端
```

关键依赖：
- 标准航迹中的 `deviceId` 必须是 `DeviceRegistry` 业务设备 id（如 `radar_001`）
- `endpointId → deviceId` 映射由输入适配阶段完成，`TrackDisplayManager` 不接触 endpoint
- `TrackDisplayManager` 只订阅 `IdentifiedTrackBatch`，不订阅厂家原始包或未识别航迹
- WS 消息为全量 snapshot（每 1s 推当前显示窗口内所有点）
- TrackDisplayManager 内部状态索引使用复合 key `(deviceId, trackId)`

## 当前 TrackPoint — 迁移期内部模型

```cpp
struct TrackPoint {
    QString deviceId;            // DeviceRegistry 业务设备 id（RadarDataProcessor 完成映射）
    uint32_t trackId;            // 航迹号
    qint64 timestampMs;
    double range;
    double azimuth;              // rad
    double elevation;            // rad
    double radialSpeed;
    double rcs;
    double altitude;
    double x, y, z;
    uint32_t sceneNumber;
};
```

- 当前代码由 `RadarDataProcessor` 输出该结构，并通过 Qt signal 直连 `TrackDisplayManager`
- `deviceId` 在 `RadarDataProcessor` 内通过 `endpointId → DeviceRegistry` 查询完成
- `TrackDisplayManager` 不查询 `DeviceRegistry`，不关心 `endpointId`
- 该直连属于迁移期实现；目标输入是总线上的 `IdentifiedTrackBatch`

## 显示缓存保留策略

上位机不判断航迹是否在物理上消失。但显示层必须有缓存保留策略：

- 不设置单条 `(deviceId, trackId)` 的固定点数上限
- 所有活动航迹共享 50000 点的显示缓存预算，超出时全局丢弃最旧点，避免某一条航迹独占内存
- 连续 5s 未更新的航迹只从显示缓存移除；这属于 UI 缓存回收，不代表上位机判定航迹消失
- 单次 snapshot 最多输出全局最新 600 个点；历史完整数据仍由 DataStore 按任务保存

## WS 消息格式（全量 snapshot）

```typescript
interface WsTrackSnapshotMessage {
  type: 'tracks'
  mode: 'snapshot'
  timestamp: number
  tracks: TrackDisplayPoint[]
}

interface TrackDisplayPoint {
  trackId: number
  deviceId: string              // DeviceRegistry 业务设备 id
  taskId: string                // 当前活动任务 id
  timestamp: number

  range: number
  azimuth: number
  elevation: number
  radialSpeed: number
  altitude: number

  // 显示状态
  pointIndex: number            // 该 (deviceId, trackId) 自接收以来绝对递增序号
                                // 不是缓存数组下标，FIFO 裁剪后不会重置
  style: {
    color: string
    size: number
    opacity: number
  }
  interaction: {
    selected: boolean
    trackingEnabled: boolean
  }
}
```

实时 Web DTO 为降低帧大小不下发内部 `x/y/z/rcs`；如后续 Web 业务需要，必须通过固定协议版本显式扩展。

## TrackDisplayManager 内部状态

```cpp
struct TrackKey {
    QString deviceId;
    uint32_t trackId;
};
```

- 内部 interaction map 及缓存均以 `TrackKey` 为索引
- 不用裸 `trackId`，避免多设备同航迹号冲突

## TrackDisplayManager 职责

- 接收 `IdentifiedTrackBatch`（已含业务 `deviceId` 和识别结果）
- 按 `TrackKey` 维护点序列和绝对递增 `pointIndex`
- 根据全局 50000 点缓存预算、5s 无更新回收和 600 点 snapshot 上限管理显示资源
- 管理 `interaction` 状态
- 根据 `pointIndex` 和用户交互状态生成 `style`
- 每 1s 输出 `TrackDisplaySnapshot`（全量当前可见点）

非职责：
- 不查询 `DeviceRegistry`
- 不关心 `endpointId`
- 不判断航迹起批、消失、融合
- 不做目标识别

## Interaction 状态更新

interaction 状态在 `TrackDisplayManager` 内部通过复合 key 维护。

```http
PUT /api/devices/{deviceId}/tracks/{trackId}/interaction
Content-Type: application/json

{
  "selected": true,
  "trackingEnabled": false
}
```

响应：

```json
{
  "ok": true,
  "interaction": {
    "taskId": "task_...",
    "deviceId": "radar_001",
    "trackId": 1,
    "selected": true,
    "trackingEnabled": false
  }
}
```

- `WebApiController` 仅接受当前活动任务内设备的命令，并将当前 `taskId` 写入 `TrackInteractionCommand`
- `TrackDisplayManager` 仅更新当前任务中仍存在的 `(deviceId, trackId)`，延迟到下一任务的命令会被拒绝
- 下次 snapshot 输出时将携带更新后的 interaction
- `selected` 与 `trackingEnabled` 独立存储

## endpointId 映射约束

`endpointId → deviceId` 映射必须唯一：

```
对于会产生航迹数据的采集 endpoint，同一时刻只能绑定一个 Radar 业务设备。
```

- `DeviceRegistry::findRadarByEndpointId(endpointId)` 提供按端点查询接口（只匹配 Radar 设备）
- 非空 `endpointId` 在 `create`/`update` 时做应用层冲突检查（同 kind=Radar 不重复）
- 活动任务正在使用的设备不得被解除端点，也不得被其他设备迁走端点
- 如果 `RadarDataProcessor` 收到数据但 `endpointId` 未绑定 Radar 业务设备：丢弃该 `TrackPoint`，不向 `TrackDisplayManager` 输出
- 如果 `endpointId` 绑定多个 Radar 业务设备：记录 `qWarning`，返回空映射，`RadarDataProcessor` 丢弃该 `TrackPoint`（宁可不显示，不挂错设备）

## 与现有模块的关系

- `InputProtocolAdapter`：厂家协议 → `NormalizedTrackBatch`，填入业务 `deviceId`
- `RecognitionModule`：`NormalizedTrackBatch` → `IdentifiedTrackBatch`；当前待实现透传识别器
- `TrackDisplayManager`：订阅识别后航迹，输出 `TrackDisplaySnapshot`
- `TrackDisplayWebBridge`：订阅显示快照并转换为固定 WebSocket DTO

当前 `RadarDataProcessor::trackPointReady -> TrackDisplayManager::addPoint` 仍是直连路径，后续应在类型安全航迹消息和透传识别器就绪后删除，不能先删除再造成显示中断。

### 前端迁移注意

- `useCoreApi.tsx`：`msg.type === 'tracks'` 当前是增量追加 `[...tracksRef.current, row].slice(-500)`。
  改为 snapshot 后应以 `msg.tracks` 替换当前显示数据，不再 append。
- `trackRate` 不能再简单 `++`，应改为 snapshot 点数或由后端提供统计字段。
- `DataTable` 如需展示"航迹列表"而非"点列表"，应按 `(deviceId, trackId)` 聚合最后一个点。
- `TrackLayer`（前端 canvas）仍为渲染层，数据格式改为全量 `TrackDisplayPoint[]`，每次 snapshot 替换上一帧。
