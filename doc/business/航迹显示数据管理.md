# 航迹显示数据管理

## 概述

上位机不负责航迹起批、消失、融合等算法（属于数据处理系统职责）。上位机负责的是航迹显示数据管理：接收 `RadarDataProcessor` 输出的航迹点，转为固定 Web 协议，维护显示状态。

## 架构边界

```
GeneralPackage → RadarDataProcessor(协议适配)
  → TrackPoint(内部通用格式，含 deviceId)
  → TrackDisplayManager(显示状态管理 + 端点→业务 id 映射)
  → TrackDisplaySnapshot(固定 Web 协议，全量 snapshot)
  → WebApiController / WS → 前端
```

关键依赖：
- `TrackPoint.deviceId` 必须是 `DeviceRegistry` 业务设备 id（如 `radar_001`）
- `endpointId → deviceId` 映射由 `RadarDataProcessor` 或 `TrackDisplayManager` 通过 `DeviceRegistry` 查询完成
- WS 消息为全量 snapshot（每 1s 推当前显示窗口内所有点）

## TrackPoint — 内部模型

```cpp
struct TrackPoint {
    QString deviceId;            // DeviceRegistry 业务设备 id（非 endpointId）
    uint32_t trackId;            // 航迹 id
    qint64 timestampMs;          // 时间戳
    double range;                // 斜距 (m)
    double azimuth;              // 方位角 (rad)
    double elevation;            // 俯仰角 (rad)
    double radialSpeed;          // 径向速度
    double rcs;                  // RCS
    double altitude;             // 高度
    double x, y, z;              // 坐标
    uint32_t sceneNumber;        // 景幅序号
};
```

- `RadarDataProcessor` 输出此结构后，后续模块不接触 `GeneralPackage`/`TargetType`
- `deviceId` 在 `RadarDataProcessor` 或 `TrackDisplayManager` 入口通过 `endpointId → DeviceRegistry` 映射完成

## 显示缓存保留策略

上位机不判断航迹是否在物理上消失。但显示层必须有缓存保留策略，防止内存无限增长：

- 每条 track 最多保留 500 个点
- 同时按时间窗口限制：最近 60s
- 超出限制时丢弃最旧的点（FIFO）
- 此策略属于显示数据管理，不属于数据处理系统的起批/消失算法

## WS 消息格式（全量 snapshot）

```typescript
// WS type: 'tracks'
interface WsTrackSnapshotMessage {
  type: 'tracks'
  mode: 'snapshot'
  timestamp: number
  tracks: TrackDisplayPoint[]
}

interface TrackDisplayPoint {
  trackId: number          // 航迹 id
  deviceId: string         // DeviceRegistry 业务设备 id
  timestamp: number

  // 坐标
  range: number
  azimuth: number
  elevation: number
  x: number; y: number; z: number

  // 运动
  radialSpeed: number
  rcs: number

  // 显示状态（TrackDisplayManager 维护）
  pointIndex: number       // 该目标第 N 个点
  style: {
    color: string
    size: number
    opacity: number
  }
  interaction: {
    selected: boolean
    trackingEnabled: boolean
  }
  routing?: {
    forwardTo?: string
  }
}
```

由 `TrackDisplayManager` 每 1s 输出一次当前可见点集（匹配显示缓存策略），`WebApiController` 直接序列化并推送。

## TrackDisplayManager 职责

- 接收 `TrackPoint`
- 通过 `endpointId → DeviceRegistry` 查询业务 `deviceId`（如已在 `RadarDataProcessor` 完成则忽略）
- 按 `trackId` 维护点序列和 `pointIndex`
- 根据缓存保留策略（500 点 / 60s）丢弃旧点
- 根据点序号和用户交互状态生成 `style`
- 管理 `interaction` 状态（用户选中、追踪使能等）
- 每 1s 输出 `TrackDisplaySnapshot`（全量当前可见点）

非职责：
- 不判断航迹起批、消失、融合
- 不做目标识别
- 不修改雷达协议数据

## Interaction 状态更新

Interaction 是 `TrackDisplayManager` 的内部状态，不只存在于前端。

```http
PUT /api/tracks/{trackId}/interaction
Content-Type: application/json

{
  "selected": true,
  "trackingEnabled": false
}
```

- 成功后 `TrackDisplayManager` 更新指定 `trackId` 的 interaction 状态
- 下次 snapshot 输出时将携带更新后的 interaction
- `selected` 与 `trackingEnabled` 独立存储，互不覆盖

## 与现有模块的关系

- `RadarDataProcessor`：保持通用包 → `TrackPoint` 适配关系
- `WebApiController`：不再直接引用 `GeneralPackage`/`TargetType`，接收 `TrackDisplaySnapshot` 并序列化推送
- `TrackLayer`（前端）：仍为 canvas 渲染层，数据格式改为 `TrackDisplayPoint[]`
- `DataTable`（前端）：仍显示航迹列表，数据源改为 snapshot
