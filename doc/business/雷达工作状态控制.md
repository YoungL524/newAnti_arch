# 雷达工作状态控制

## 概述

控制雷达进入工作模式（开始上报航迹）或待机模式（停止上报）。web 端"开始采集"按钮位于 TitleBar 顶层，是雷达控制的核心入口。

**核心原则**（目标架构）：
- **设备级独立控制**：每台雷达有独立的状态机，可单独启停
- **命令广播下发**：workStandby 通过 SystemBus→UDP 广播给所有雷达 CPU，各雷达按需接收
- **故障即时反馈**：任意雷达异常时 UI 立即告警（设备报红、PPI 扫线停止）

### 当前实现范围（单控制器 MVP）

当前代码尚未实现「每台雷达一个 `RadarWorkModeController`」。实际为：

- `AppController` 仅持有一个 `RadarWorkModeController`，对应 `radar_cpu` 端点
- `POST /api/start`、`/api/stop`、`/api/reset` 虽接收 `deviceIds`，但命中第一个映射到 `radar_cpu` 的设备后即执行一次命令并结束
- `GET /api/status` 与 WS status 中，所有 `endpointId == radar_cpu`（或 `id == radar_cpu`）的业务设备**共享同一状态**

`deviceIds` 字段是**为多控制器扩展预留的 API 契约**，当前阶段不代表逐设备独立执行。响应中 `mode: "single-controller"` 与 `controllerId: "radar_cpu"` 用于标明这一语义。

下一阶段多雷达控制需引入 `WorkModeControllerRegistry`（如 `QHash<QString, RadarWorkModeController>`），届时 `/api/status` 才返回每台设备各自的真实状态。

## 用户操作流程

**目标架构示例**（多控制器落地后的预期行为）：

```
已注册设备列表:
  ☑ NODE_ALPHA_01  中电38所 · 4面 · 5km    ● 待机
  ☑ NODE_BETA_02   中电14所 · 1面 · 3km    ● 待机
  ☐ NODE_GAMMA_03  雷鹰   · 2面 · 8km    ● 待机

          用户勾选 2 台 → 点击 [开始采集]
                    │
                    ▼
          已勾选的 2 台进入工作模式
          未勾选的 NODE_GAMMA_03 保持待机
```

**当前 MVP**：勾选多台时，仅**第一个**映射到 `radar_cpu` 的设备 id 触发控制器命令，其余 mapped id 进入 `rejectedDeviceIds`；未映射设备同样 rejected。所有 `radar_cpu` 映射设备在 UI 上共享同一状态显示。

**无勾选时**：点击"开始采集"弹出引导弹窗，提示用户至少选择一台雷达。

**设备状态指示**（设备列表每行右侧）：

| 圆点颜色 | 状态 | 含义 |
|----------|------|------|
| `#94a3b8` 灰 | Standby | 待机 |
| `#22c55e` 绿 | Starting/Working | 工作中或启动中 |
| `#ef4444` 红 | Fault | 故障 |
| — 无 | Stopping | 过渡中，临时不显示 |

## 触发路径

```
Web UI                                     core 控制台
  │                                             │
  │ 勾选设备 → [开始采集]                        │
  │    │                                        │
  │    ▼                                        ▼
  │ POST /api/start { deviceIds: [...] }   stdin: "1" 或 "work"
  │    │                                  stdin: "0" 或 "standby"
  │    │                                        │
  │    ▼                                        ▼
  │ RadarWorkModeController（当前单实例；目标为每雷达一个）
  │    .requestWork() / requestStandby() / reset()
  │    │                                        │
  │    ▼                                        │
  │ BusWorkModeSender → SystemBus.publish() ────┘
  │    │
  │    ▼ (广播到所有雷达 CPU)
  │ BusToCommRouter → CommManager → UDP → 雷达 CPU
  │
  └─── GET /api/status → 返回设备状态（当前：radar_cpu 映射设备共享同一状态）
       WS broadcast 每 1s 推送设备状态
```

**注意**：console 入口的 stdin 命令控制全部已配置雷达（全局工作/待机），与 web UI 的设备级勾选是两套操作入口。

## 输入值约定

| 输入值 | 含义 | HTTP 端点 | stdin 命令 |
|--------|------|-----------|------------|
| `workStandby_Mode = 1` | 工作（开始上报航迹） | `POST /api/start` | `1` / `work` |
| `workStandby_Mode = 0` | 待机（停止上报航迹） | `POST /api/stop` | `0` / `standby` |

HTTP 端点 body 示例：

```json
// 启动指定设备
POST /api/start
{ "deviceIds": ["dev_1717000000_1", "dev_1717000000_2"] }

// 关闭指定设备
POST /api/stop
{ "deviceIds": ["dev_1717000000_1"] }

// 复位故障控制器（body 为空时作用于 radar_cpu）
POST /api/reset
{ "deviceIds": ["dev_1717000000_1"] }

// 空 body = 控制 radar_cpu 控制器（单控制器 MVP）
POST /api/start
{}
```

单控制器阶段，`acceptedDeviceIds` 仅包含**实际执行**的那一个 id；若请求含多个映射到 `radar_cpu` 的设备，其余进入 `rejectedDeviceIds`。响应含 `mode: "single-controller"` 与 `controllerId: "radar_cpu"`。

## 设备状态机

**目标架构**：每台雷达独立运行以下状态机。**当前 MVP**：所有映射到 `radar_cpu` 的设备共享下方同一状态机实例。

```
              requestWork (send ok)
    Standby ───────────────────────► Starting ───(超时 300ms)──► Working
       ▲                                                           │
       │                                            requestStandby (send ok)
       │                                                           │
       │                                                           ▼
    Standby ◄─────────────────────── Stopping ◄──(超时 300ms)─── Working

    任意状态 + send 失败 ──► Fault
    Fault   + reset ──► Standby
```

| 状态 | 含义 | 设备列表表现 | PPI 扫线 |
|------|------|-------------|----------|
| Standby | 待机 | 灰色圆点 · 待机 | 停止 |
| Starting | 命令已发出，等待确认 | 绿色圆点 · 启动中 | 停止（等待确认） |
| Working | 工作中，雷达上报航迹 | 绿色圆点 · 工作中 | 运行 |
| Stopping | 停机命令已发出 | 无圆点（过渡） | 运行（到确认前） |
| Fault | 故障 | **红色圆点 · 故障** | 停止 |

### 过渡超时（临时乐观确认）

当前实现中，Starting/Stopping 若在超时（默认 300ms）内未收到雷达 workmode 回显，则按成功处理：

- Starting 超时 → Working
- Stopping 超时 → Standby

这表示**上位机控制状态**的乐观确认，不代表雷达已真实 ACK。后续若协议提供明确回显，应改为：收到匹配 ACK 才切换；超时无 ACK 进入 Fault。

UI 上的「工作中」应理解为上位机控制语义，而非绝对设备物理状态。

## 多设备状态聚合

前端 TitleBar 按钮状态由**勾选设备的聚合状态**决定：

| 勾选设备状态 | 按钮显示 | 可点击 |
|-------------|----------|--------|
| 全部 Standby | 开始采集 | 是 |
| 全部 Working | 停止采集 | 是 |
| 混合（部分工作部分待机） | 停止采集 | 是（停止全部工作设备） |
| 任意设备 Fault | **复位** | 是（复位 `radar_cpu` 控制器；当前为全局复位） |
| 任意设备过渡中 | 开始采集/停止采集（灰） | 否 |

## 前端联动

### 状态同步

1. **HTTP 轮询**（每 5 秒）：`GET /api/status` → `{ devices: [{ id, state }], connected }`
2. **WebSocket 推送**（每 1 秒）：`{ type: "status", devices: [...] }`

### PPI 扫线与设备状态绑定

- PPIOverlay 的 `acquiring` 不再用全局标志，改为读对应雷达设备的状态
- Working 状态 → 扫线运行
- 非 Working 状态 → 扫线停止（不画）
- Fault → 扇区边框变红、扫线停止、中心点红色

### 设备列表状态指示

设备列表每行末尾渲染状态圆点，颜色由设备当前 state 决定。

## 异常处理

| 异常 | 设备状态 | UI 反馈 | 恢复方式 |
|------|---------|---------|----------|
| sender 为 nullptr | Fault | 设备行报红 + PPI 中心点变红 | 复位 |
| send 返回 false | Fault | 同上 | 复位 |
| 后端未运行 | — | 轮询失败，connected=false | 启动 core.exe |
| 某台雷达 CPU 不可达 | 控制器进入 Fault | 映射设备均报红（当前共享状态） | 复位 |

## 设计要点

- **隔离原则**（目标架构）：一台雷达的故障不影响其他雷达。当前单控制器阶段，Fault 影响所有 `radar_cpu` 映射设备的显示状态
- **DPH 持续发送**：DphPublisher 每 50ms 独立发送 DPH 报文，不受状态机影响。状态机只改变报文中的 `workStandby_Mode` 字段
- **广播命令**：workStandby 命令通过 SystemBus 发布后，BusToCommRouter 转发到所有订阅的 UDP 端点，各雷达 CPU 自行判断是否响应
- **幂等**：重复发送相同 workStandby_Mode 的 DPH 不会造成问题
- **过渡态保护**：Starting/Stopping 期间锁定输入

## 依赖

```
HttpServer (POST /api/start|stop|reset)
  └── AppController
        └── RadarWorkModeController  (当前单实例，key=radar_cpu；目标为每雷达一个)
              ├── IWorkModeCommandSender → BusWorkModeSender
              │     └── SystemBus.publish()  (广播命令)
              └── QTimer (过渡超时)
```
