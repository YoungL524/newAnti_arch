# 任务数据自动归属 - 单任务实现

## 目标

实现一个很小但关键的能力：

> 当前激活任务绑定了哪些设备，这些设备产生的航迹数据就自动归属到当前任务。

不要做“手动绑定航迹到任务”的功能。  
不要让前端决定航迹属于哪个任务。  
不要要求雷达协议携带我们的业务 `deviceId`。

## 核心原则

已有 `DataPacket.sourceType`，它就是数据来源字段，不要再造新的“数据源”概念。

三层关系如下：

```text
通信端点 / 协议来源
endpointId + sourceType
        |
        v
后端设备台账
DeviceRegistry.deviceId
        |
        v
当前激活任务
TaskService.activeTask().deviceIds
        |
        v
数据归属
taskId
```

外部雷达只需要从已配置端点上报协议数据。  
业务 `deviceId` 只由后端设备台账生成和维护。  
前端只选择后端已有设备，不生成最终设备 id。  

## 判断规则

收到一条航迹数据时：

1. core 知道数据来自哪个 `endpointId`。
2. core 根据协议/配置得到 `sourceType`。
3. core 通过 `DeviceRegistry` 把 `endpointId/sourceType` 映射成业务 `deviceId`。
4. core 读取当前 active task。
5. 如果 `deviceId` 在 active task 的 `deviceIds` 中，则这条数据归属当前 `taskId`。
6. 如果没有 active task，或设备不属于当前任务，则这条数据不写入任务历史。

一句话：

```text
sourceType/endpointId -> deviceId -> activeTask.deviceIds contains(deviceId) -> taskId
```

## 本次只做什么

### 1. 增加当前任务上下文查询

可以先不做复杂服务，最小实现即可：

- 在需要写入航迹的地方能拿到 `TaskService::activeTask()`。
- 能判断某个 `deviceId` 是否属于当前 active task。

建议封装一个小函数，避免逻辑散落：

```cpp
QString resolveActiveTaskIdForDevice(const QString& deviceId);
```

返回规则：

- 有 active task 且包含 deviceId：返回 taskId。
- 否则返回空字符串。

后续如果逻辑变复杂，再升级成 `ActiveTaskContext`。

### 2. tracks 表增加 task_id

当前 `tracks` 表已有 `source` 字段，不要删除。

本次只新增：

```sql
task_id TEXT
device_id TEXT
```

说明：

- `task_id` 是任务归属。
- `device_id` 是后端设备台账 id，方便查询。
- `source` 继续保留 endpoint/source 字符串，方便排查原始来源。

建议索引：

```sql
CREATE INDEX IF NOT EXISTS idx_tracks_task_ts ON tracks(task_id, ts_ms);
CREATE INDEX IF NOT EXISTS idx_tracks_task_device ON tracks(task_id, device_id);
```

### 3. RadarDataProcessor 写入航迹时自动补 task_id

当前流程里已经有：

```cpp
endpointId -> DeviceRegistry::findRadarByEndpointId(endpointId) -> deviceId
```

本次改造：

- 找到 `deviceId` 后，再查当前 active task。
- 如果 deviceId 属于 active task：
  - `tracks.task_id = activeTask.id`
  - `tracks.device_id = deviceId`
  - 正常入库
- 如果不属于：
  - 不写入任务历史
  - 实时显示是否保留，先按当前行为不强改

注意：

`DataPacket.sourceType` 仍然是来源字段。  
`device_id` 不是新来源，只是后端业务设备 id 的落库副本。

## 暂时不要做什么

不要做以下内容：

- 不做回放 API。
- 不做复杂历史查询 UI。
- 不改 DPH。
- 不改 SystemBus 生命周期。
- 不让前端传 taskId 给航迹。
- 不要求雷达协议携带业务 deviceId。
- 不做多任务同时归属。
- 不做多 active task。

## 验收标准

1. 创建任务 A，绑定设备 `radar_001`。
2. 激活任务 A。
3. `radar_001` 对应端点上报航迹。
4. `tracks` 表新增记录包含：

```text
task_id = 任务A.id
device_id = radar_001
source = 原 endpoint/source
```

5. 如果激活任务 A，但另一个未绑定设备上报航迹，则不写入任务 A 的历史。
6. 如果没有 active task，上报航迹不写入任务历史。

## 给 Cursor 的实现顺序

1. 给 `tracks` 表补 `task_id`、`device_id` 字段和索引。
2. 让 `RadarDataProcessor` 能访问 `TaskService` 或一个轻量 task resolver。
3. 在航迹入库前完成：

```text
endpointId -> deviceId -> activeTask -> taskId
```

4. `bufferTrack()` 增加 `taskId/deviceId` 写入。
5. 补最小日志，打印“航迹归属 taskId/deviceId”或“不属于当前任务，跳过归档”。
